## 1. 전장 구조

세븐나이츠식 **전열/후열** 구조다. 각 진영은 2열이고, **한 열에 4명**이 세로로 늘어선다.

```
   아군 후열   아군 전열        적 전열   적 후열
    (x=-2)     (x=-1)          (x=1)    (x=2)
      □          □      ⚔       □         □      y=1
      □          □              □         □      y=2
      □          □              □         □      y=3
      □          □              □         □      y=4

              대기석  □ □ □ □ □   (전투 미참여)
```

| 항목 | 값 | 코드 |
| --- | --- | --- |
| x 범위 | `[-2, 2]`, **`x = 0` 없음** | `GridManager.xMin/xMax` |
| y 범위 | `[1, 4]` | `GridManager.yMin/yMax` |
| 진영당 | **2열 × 4행 = 8칸** | |
| 전열 | `x = ±1` | `GetFrontColumn()` |
| 후열 | `x = ±2` | |
| 대기석 | **5칸** | `GridManager.benchSize` |

### 1.1 화면 배치 상수

**두 축 모두 등간격**이다. 진영마다 반듯한 2 × 4 격자가 나온다.

| 상수 | 값 | 의미 |
| --- | --- | --- |
| `ColumnSpacing` | 11.6 | 같은 진영 두 열 사이의 거리 |
| `SlotSpacing` | 11.6 | 한 열 안 4명의 간격 |
| `CenterGap` | 7 | 양 진영 사이에 추가로 벌리는 거리 |
| `BenchOffsetY` | 14 | 전장 최하단에서 대기석까지 |
| `Cell.StandingHeight` | 8.6 | 캐릭터 스프라이트 최대 높이 |
| `Cell.StandingWidth` | 9 | 캐릭터 스프라이트 최대 너비 |

결과 좌표 — x는 ±9.3(전열) / ±20.9(후열), y는 +17.4 / +5.8 / −5.8 / −17.4.

> **간격은 칸 크기(10.16)보다 항상 커야 한다.**
> 예전에는 유사 3D 원근을 넣어 뒤 행 간격이 `SlotSpacing × 0.82`까지 줄었고,
> 캐릭터 높이도 13이라 **칸보다 캐릭터가 커서** 위 행의 타일과 체력 바를 뚫고 올라갔다.
> 그래서 유닛들이 서로 겹쳐 보였다. 원근을 걷어내고 캐릭터를 칸 안에 넣어 해결했다.
> 캐릭터는 칸 정중앙에 서고, 체력 바는 정수리 바로 위(`높이/2 + 0.7`)에 붙는다.

### 1.2 배치 규칙

| 대상 | 규칙 |
| --- | --- |
| 아군 | 전열(−1) 우선, 가운데 행(y=2,3)부터 채운다 — `TryFindOpenAllyPosition` |
| 적 | `archetype` 7·8·9 → 전열(x=1), 그 외 → 후열(x=2). 각 열 최대 4 — `GetColumnForArchetype` |

- 셀 이름 규칙: `Cell_x_y`
- 실제 출전 인원은 파티 상한(5명)에 종속된다 — 8칸을 다 채울 수 없다
- 대기석 유닛은 전투 판정과 UI 모두에서 제외된다
- 유닛 사망 시 셀은 **2초 예약 대기** 후 재사용 가능해진다

## 2. 행동 순서 — 턴제 + 행동치(AV)

**시간 축은 초가 아니라 턴이다.** 벽시계는 연출(투사체 비행·시전 모션)에만 쓴다.
지속시간·주기·내부 쿨다운·제어는 전부 턴으로 센다.

### 2.1 턴의 정의

> **턴 = 그 효과를 들고 있는 유닛이 행동하는 것.**

| 대상 | 누구의 턴으로 세는가 |
| --- | --- |
| 버프·디버프·지속피해 | **상태가 붙어 있는 유닛** |
| 주기형 패시브(빅뱅) | **패시브 보유자** |
| 소환수(마카라) | **소환자** |
| 원소 부착 | **부착된 유닛** |

규칙이 하나라 예외가 없다. 상태는 자기 보유자의 턴에, 패시브는 자기 시전자의 턴에 진행된다.
진행 지점은 `Unit.BeginTurn()` 한 곳이다.

### 2.2 AV — 다음 행동자 결정

```
속도 = 100 × ActionSpeedCurr        (ActionSpeedCurr = 1 + 최종 DEX × 0.01)
AV   = 10000 / 속도                 (작을수록 먼저 행동)
```

시간을 흘려보내지 않는다. **AV가 가장 낮은 유닛이 0에 닿을 만큼만 전원의 AV를 한 번에 깎고**,
그 유닛이 행동한 뒤 자기 AV를 가득 채운다. 프레임 수·연출 길이가 순서에 영향을 주지 않는다.

동점이면 속도가 빠른 쪽이 먼저다.

### 2.3 우선순위 — 한 번에 하나만

큐에 오르는 것은 **행동**뿐이다. 패시브 코드처럼 행동을 *호출*하는 쪽은 줄을 서지 않는다 —
호출된 결과가 행동으로 예약될 뿐이다. 구분은 [Detail_03 §4.5-A](Detail_03_Character.md)에 있다.

| 순위 | `ActionKind` | 행동 | 턴 |
| ---: | --- | --- | :-: |
| 0 | `PriorityAdditional` | **우선 추가행동** — 패시브가 부른 것 | 안 쓴다 |
| 1 | `Special` | **특수행동** — 인드라의 궁극기만이 연다 | 안 쓴다 |
| 2 | `Additional` | **추가행동** | 안 쓴다 |
| 3 | `Ultimate` | **궁극기** | 안 쓴다 |
| 4 | `Normal` | **일반행동** 또는 그 자리를 대신 쓰는 **대체행동** | 쓴다 |

**특수행동은 추가행동과 판정이 다르다.** 턴을 쓰지 않는 성질만 같고 `OnSpecialActivates`를
따로 발행하므로 추가행동 카운터(바스테트)에는 잡히지 않는다.
규칙은 [Detail_03 §4.5-C](Detail_03_Character.md)에 있다.

0과 1은 **성질이 같다.** 패시브가 불렀다는 이유로 먼저 나갈 뿐이고, 둘 다 턴을 쓰지 않으며
`OnAdditionalActivates`를 발행한다(`ActionScheduler.IsAdditional`).
세이의 `빅뱅`이 0번이며, 그래서 니콜의 행동 카운터와 바스테트의 스택이 빅뱅도 센다.

**중복 방지** — 같은 `(유닛 + 종류 + 키)` 조합은 큐에 하나만 존재한다.
추가행동이 여러 번 겹쳐 터지거나 한 턴에 본 행동이 두 번 잡히지 않는다.

**궁극기는 턴을 쓰지 않는다.** 자원이 차는 즉시 누구의 턴이든 줄을 서고, 발동해도 AV가
리셋되지 않아 원래 예정된 일반행동 차례는 그대로 남는다.

### 2.4 초 → 턴 환산

기존 수치는 **2초 = 1턴**(반올림, 최소 1)으로 옮겼다.

| 예전 | 지금 |
| --- | --- |
| 창세 8초 | 4턴 |
| 빅뱅 6초마다 | 3턴마다 |
| 마카라 8초 지속, 2초마다 | 4턴 지속, 1턴마다 |
| 원소 부착 9.5초 | 5턴 |
| 화상 기본 / 감전 4초 | 2턴 / 2턴 |
| 치유량 감소 6초 | 3턴 |

**매초 N 피해**였던 지속피해는 **턴당 2N**이 됐다. 1턴이 2초에 해당하므로 체감 총량은 같다.

지속피해가 **대상의 턴**에 터지므로 느린 적일수록 도트가 천천히 들어간다.
이건 의도된 성질이다 — 야마처럼 지속피해를 직접 터뜨리는 전문 유닛의 자리를 만든다.

### 2.4-C 주기 패시브는 자기 턴 수로 센다

**주기형 패시브는 보유자의 턴 수만 센다.** `Codes/Base/PeriodicTurnPassive.cs`가 공통 뼈대다.
`intervalTurns`를 주면 자기 턴이 그만큼 열릴 때마다 `OnPeriodElapsed()`가 불리고,
사망·라운드 종료에 스스로 구독을 끊는다.

| 훅 | 쓰임 |
| --- | --- |
| `fireOnStart` | 전투 시작 시 한 번 먼저 발동 (부름 · 날개 달린 뱀) |
| `CanTick()` | 세지 않을 턴을 걸러낸다 (보호막 대기 중 · 행동 불가) |
| `ResetPeriod()` | 조건을 소비했을 때 주기를 처음부터 |
| `RetryNextTurn()` | 이번 발동이 실패했을 때 (자리가 없어 소환 실패) |

예전에는 각 코드가 `OnTurnStart`에서 **흐른 전투 시계 초를 누적**해 주기를 쟀다. 같은 누적기가
파일마다 복사돼 있었고, 초 축은 DEX가 빠를수록 같은 초에 턴이 더 많이 들어가
**빠를수록 주기가 늦게 오는 역전**을 만들었다. 그보다 더 전에는 `OnUpdate` 프레임 훅에서
`Time.deltaTime`을 더해, 긴 궁극기 연출을 보고 있으면 재생력이 그만큼 더 회복했다.
지금 프레임 훅은 연출 전용이며 전투 판정에는 쓰지 않는다.

해당 코드 — 막기 · 날개 달린 뱀 · 주문 보호막 · 변덕쟁이.
철벽과 사막의 피도 턴을 세지만 주기가 아니라 행동·조건에 반응하므로 이 뼈대를 쓰지 않는다.

### 2.4-A 라운드 제한 — 턴 수

라운드는 **전역 80턴**으로 끝난다(`GameManager.roundTurnLimit`). 추가행동·패시브 발동은 세지 않는다.

초로 재면 시전 딜레이·투사체 비행 같은 **연출 길이가 라운드당 행동 수를 좌우**한다.
연출을 손볼 때마다 밸런스가 흔들리므로 턴으로 센다.
참가 유닛이 많을수록 각자 얻는 턴은 줄어드는데, 인원이 적은 보스전에 더 많은 턴이
돌아가는 셈이라 의도한 성질이다.

### 2.4-B 궁극기 자원 — INT × 전투 시간

```
초당 회복 = (1.5 + INT × 0.15) × 마나 회복 효율        (상한 20/초)
자원 최대 = 100
```

**행동 횟수와 무관하다.** 예전에는 일반행동 1회에 고정량을 얻어 고DEX 유닛일수록 궁극기가
빨리 찼고 INT는 곁가지 배율에 그쳤다. 지금은 전투 시간에 비례하므로
**느리더라도 INT가 높으면 궁극기로 화력을 내는 빌드**가 성립한다.

| INT | 초당 | 100까지(전투 시간) |
| ---: | ---: | ---: |
| 8 | 3.1 | 32초 |
| 18 | 5.7 | 18초 |
| 24 | 7.6 | 13초 |
| 40 | 13.5 | 7초 |
| 100+ | 20 (상한) | 5초 |

기본 회복량과 마나 회복 효율이 둘 다 INT에 비례해 사실상 INT의 제곱으로 자란다.
고레벨 캐스터가 매 턴 궁극기를 쓰는 것을 막으려고 초당 20의 뚜껑을 씌웠다.

### 2.5 전투 시계 — 궁극기 자원 전용

전투 판정의 시간 축은 **턴 하나뿐이다.** 초는 궁극기 자원 충전 한 곳에만 남아 있다.

```
흐른 전투 시간(초) = 이번 턴에 깎인 AV ÷ 40
```

벽시계가 아니다. **AV가 흐른 만큼만** 늘어나므로 누군가 행동하는 동안에는 멈추고,
연출 길이·프레임 수·배속은 영향을 주지 않는다. 추가행동·패시브 발동처럼
AV를 쓰지 않는 행동도 시간을 흘리지 않는다.

환산 계수 40(`ActionScheduler.ActionValuePerSecond`)은 실시간 모델이던 시절의 초당 AV
감소량이다. 그래서 **속도 100(DEX 0)이면 2.5초마다 행동한다**는 감각이 그대로 유지된다.

| 축 | 쓰는 곳 |
| --- | --- |
| **턴** (`Unit.TurnCount`) | 지속시간 · 주기 패시브 · 내부 쿨다운 · 제어 · 지속피해 — **전부** |
| **전투 시간** (AV ÷ 40) | 궁극기 자원 충전(`Unit.AccrueUltimateResource`) 하나뿐 |

> 예전에는 `ActionScheduler.CombatSeconds`와 `Unit.LastTurnSeconds`가 공개 축으로 있었고,
> 초 단위로 기획된 주기형 효과가 턴 경계에서 그 값을 누적했다. 주기가 전부 턴으로 옮겨진 뒤
> 읽는 곳이 없어져 두 프로퍼티를 지웠다. **초로 새 효과를 기획하지 않는다.**

### 2.6 어떤 코드에도 재사용 대기 시간이 없다

**일반행동은 AV가, 궁극기는 자원이 주기를 정한다.** `Code.Cooldown`과
`Unit.ultimateCooldown`은 삭제됐고, 궁극기는 자원이 가득 차는 순간 곧바로 줄을 선다.

> 예전에는 궁극기에 **자원과 쿨다운이라는 관문이 둘** 겹쳐 있었다.
> 쿨다운이 4턴인데 자원이 3턴 만에 차면 남은 1턴 동안 INT를 아무리 올려도
> 궁극기가 빨라지지 않는다. 충전 축을 INT 하나로 세운 설계와 정면으로 부딪히므로
> 관문을 자원 하나로 줄였다. 일반행동이 AV 하나만 보는 것과 같은 이유다.

"쿨다운을 깎는다"였던 효과는 두 갈래로 옮겨졌다.

| 예전 | 지금 |
| --- | --- |
| 행동을 앞당긴다 | `ActionScheduler.AdvanceAction(unit, ratio)` — 남은 AV를 `ratio`만큼 당겨 온다 |
| 궁극기를 앞당긴다 | `Unit.AddUltimateResource` / `RecoverMana`로 자원을 직접 채운다 |

**코드 가속(`CodeAcceleration`)의 자리도 바뀌었다.** 쿨다운 감소량을 키우던 값이었으므로
쿨다운이 사라지면 읽는 곳이 없다. 지금은 `Unit.ManaPerCombatSecond`에 곱해져
**궁극기 자원 충전 속도**를 올린다. 충전 상한 안쪽에서 곱하므로 최단 주기 5초는 그대로다.
1 미만의 코드 가속은 이제 실제로 충전을 늦춘다 — 예전 쿨다운 감산에는 최소 1턴 바닥이 있어
감속 효과가 사실상 사문이었다.

일반행동 차단은 `BaseEffect.BlocksNormalAttack`으로 판정한다.

**코드 안쪽 내부 쿨다운도 턴으로 잰다** — `Combat/TurnCooldown.cs`의 `TurnCooldown`(자기 전용)과
`TargetTurnCooldown`(대상별). 예전에는 `Time.time` 벽시계를 써서 배속(F4)을 올리면
같은 전투에서 내부 쿨다운이 더 자주 돌았다.

## 3. 피해 계산

### 3.1 파이프라인

```
1) OnBeforeDamageTaken           (자신, 공격자)
2) 회피 판정                      EvasionChanceCurr
3) OnTakingDamage                 실제 계산 (아래 3.2)
4) 보호막 흡수 → 체력 차감
5) 사망 방지 판정                  BaseEffect.TryPreventDeath
6) OnAfterDamageTaken            (자신, 공격자)
7) OnDamageDealt                 (공격자에게 실제 가한 피해량 전달)
8) 체력 0 이하 → Die() → OnDeath
```

### 3.2 공식 — 포켓몬식 위력 + 롤 방식 방어력

```
기본피해   = 스킬 위력 × 시전자 주스탯 × 0.2
유효방어력 = max(0, 방어력 − 관통) × 방어무시배율
방어배율   = 기준값 / (기준값 + 유효방어력)          // 방어력 ≥ 0
           = 2 − 기준값 / (기준값 − 유효방어력)      // 방어력 < 0
최종피해   = max(1, round(min(기본피해 × 치명타 × 주는피해보정 × 방어배율 × 받는피해보정 − 내구,
                            최대체력 × 한방상한)))
```

| 요소 | 출처 |
| --- | --- |
| 스킬 위력 | `Code.CurrentPower` — 아래 3.2-A |
| 주스탯 | 시전자의 `mainStat` (스킬이 다른 스탯을 지정할 수도 있다) |
| **방어력** | **STR × 1** (`UnitStats.DefensePerStrPoint`) — 비율 감소 |
| **내구** | 착용 방어구의 `durability` 합 — **고정 감소** |
| 기준값 | `100 + 10 × (레벨 − 1)` (`ArmorConstantBase` / `ArmorConstantPerLevel`) |
| 주는/받는 피해 보정 | `OutgoingDamageModifier` / `ReceivingDamageModifier` 누적곱 |

`DamageTag.TrueDamage`가 붙은 피해는 방어 감쇠를 건너뛴다.
`DamageTag.DurabilityPenetration`이 붙은 피해는 마지막의 내구 차감을 건너뛴다.

### 3.2-B 한 방 상한 — 최대 체력 비례

`BaseEffect.IncomingDamageCapRatio`가 0보다 크면 **감쇠와 내구를 모두 통과한 뒤** 그 값으로
자른다. 여러 효과가 걸리면 **가장 낮은 비율**이 이긴다.

| 코드 | 상한 | 대상 |
| --- | --- | --- |
| 알파 개체(1541) | 최대 체력의 1/2 | 모든 피해 |
| 완전함(1546) | 최대 체력의 1/3 | 모든 피해 |
| 질량(1580) | 최대 체력의 1/4 | 단일 대상 피해만 |

**체력 바를 칸으로 나눠 그리는 `HpSegmentCount`는 표시일 뿐 피해를 자르지 않는다.**
"한 방에 절반 넘게 깎이지 않는다"를 실제로 만들려면 감쇠가 끝난 값을 잘라야 하므로 훅을 따로 뒀다.
상한이 없으면 최대 체력을 배로 불려도 광역 폭딜 한 번에 통째로 사라져
**최대 체력만 키운 것과 다르지 않다.**

### 3.2-A 위력의 두 형식

```
고정형   위력 = Power (또는 StagePowers[단계])
비례형   위력 = 고정값 + 시전자 스탯 × 계수      (Code.PowerStatCoefficient / PowerStat)
```

기본은 고정형이다. 비례형은 **저점을 고정값으로 보장하고 고점을 억제하는** 형식으로,
로마 테마 전체가 이 형식을 쓴다.

| 표기 | 고정값 | 계수 | 성격 |
| --- | ---: | ---: | --- |
| `위력 50 + STR×0.2` | 50 | 0.2 | 초반부터 일정한 화력. 후반 성장 완만 |
| `위력 DEX×0.6` | 0 | 0.6 | 순수 비례. 초반이 약한 대신 성장 폭이 크다 |

**계수를 크게 잡으면 위험하다.** 위력 자체가 스탯에 비례하면 최종 피해가
`스탯²`에 가깝게 자라기 때문이다. 그래서 로마 테마의 계수는 0.2~1.6 범위에 묶여 있다.

같은 이유로 보호막도 비례형을 쓸 수 있다. 하스타티 계열의 전투 시작 보호막이
`위력 200 + CON×1.0`이고, 실제 양은 그 위력에 CON을 다시 곱해 산출한다.

#### 기준값이 레벨에 비례하는 이유

리그 오브 레전드는 기준값이 100 고정이지만, 롤은 아이템으로 피해가 초선형 성장한다.
이 게임은 **모든 스탯이 레벨에 선형 비례**하므로 기준값을 100으로 두면
방어력만 계속 커져 후반에 피해가 무한히 상쇄된다.

기준값을 레벨과 함께 키우면 **감소율이 레벨과 무관하게 일정**해진다.

| | Lv.1 | Lv.10 | Lv.50 | Lv.100 |
| --- | --- | --- | --- | --- |
| 무르밀로 (STR 낮음) | 12% | 12% | 11% | 11% |
| 스파르타쿠스 (STR 높음) | 33% | 33% | 33% | 33% |

즉 **방어력은 캐릭터의 정체성이지 레벨의 함수가 아니다.**

#### 내구 — 고정 경감

방어력이 **비율**로 깎는다면 내구는 **절대량**으로 깎는다.
계산의 맨 마지막에 적용되며, **방어 무시·관통의 영향을 전혀 받지 않는다.**

| 성질 | 결과 |
| --- | --- |
| 방어 무시 빌드에 남는 최후의 완충재 | 수르트처럼 방어력을 100% 무시해도 내구는 그대로 깎인다 |
| **다단히트에 특히 강하다** | 발마다 고정값이 빠지므로, 6발로 나눠 때리면 6번 깎인다 |
| 지속피해에는 적용하지 않는다 | 틱당 피해가 작아 내구가 곧 무효화가 되어 버린다 |

**다단히트 대비 효과 (내구 10 기준)**

| 공격 형태 | 총 피해 | 내구 적용 후 | 경감률 |
| --- | --- | --- | --- |
| 1발 300 | 300 | 290 | 3% |
| 6발 × 59 | 354 | 294 | **17%** |

즉 내구는 **저타수 고위력보다 다단히트를 훨씬 강하게 억제한다.**
세이식 유도탄 빌드에 대한 자연스러운 대항 수단이 된다.

> **고정값이므로 티어를 따라 올려야 후반에도 의미가 남는다.**
> 티어 × 분류별 내구 표는 [Detail_14 §2.4](Detail_14_Equipment_Catalog.md)에 한 벌만 둔다.

#### CON과 STR의 역할 분담

| 스탯 | 내구 기여 | 성격 |
| --- | --- | --- |
| CON | 최대 체력 (절대량) | 한 방을 크게 버틴다 |
| STR | 방어력 (비율 감소) | 큰 피해일수록 많이 깎는다 |
| 장비 | 내구 (고정 감소) | 잔타를 무력화한다 |

실효 체력 = `체력 ÷ 방어배율`. 둘을 곱셈으로 쌓으므로 한쪽만 올리면 효율이 떨어진다.

**위력 기준선**

| 구간 | 위력 |
| --- | --- |
| 일반행동 | 38~70 |
| 패시브 연계타 | 60~150 |
| 궁극기 | 75~150 |

> 구 계수 체계에서 옮길 때는 **위력 = 기존 계수 × 50**을 썼다(계수 1.0 → 위력 50).

**기획 사양의 "스탯의 N%" 표기 = 위력 N**

캐릭터 사양서는 "INT의 40%에 해당하는 피해"처럼 적는다. 이를 코드로 옮길 때는
**N을 그대로 위력으로 읽는다** (`SkillDamage(40, PrimaryStat.INT)`).

문자 그대로 `INT × 0.4`로 구현하면 안 된다 — INT가 20~30대이므로 피해가 10 남짓이 되어
체력 1,200~35,000인 적에게 아무 의미가 없다. 실제로 츠쿠요미·찬드라가 그 상태였다.

**보호막·회복도 같은 척도를 쓴다.** "CON의 100%에 해당하는 방어막" → `SkillDamage(100, CON)`.

## 4. 보호막

| 규칙 | 내용 |
| --- | --- |
| 우선순위 | 체력보다 **먼저** 소모 |
| 관통 예외 | `DamageTag.ShieldPenetration` 피해는 보호막 무시 |
| 지속피해 예외 | `CodeType.Effect` (맹독·화상 등)는 보호막을 무시하고 체력에 직접 적용 |
| 부여량 증폭 | CON 기반 `ShieldBonusCurr` 적용 (`AddShield` / `SetShield`) |
| 소진 처리 | `ShieldCurr`가 0이 되면 `ShieldMax`도 0으로 초기화 |
| 지속 | 라운드 내 유지, `OnRoundEnd`에 정리 |

**흡수 처리**

```
보호막 >= 피해 : 보호막 −= 피해,  체력 변화 없음
보호막 <  피해 : 체력 −= (피해 − 보호막),  보호막 = 0
```

## 4-A. 파생 전투 규칙

2026-08 신규 캐릭터군(프레이아·로키·스카디·쿠베라·바루나·오르페우스·스사노오)이 도입한 규칙이다.

### 4-A.1 순수치유량

| 항목 | 내용 |
| --- | --- |
| 정의 | 실제로 체력을 채운 양. **과다치유(오버힐)를 뺀 값** |
| 제외 | 보호막, 과다치유→보호막 전환분, 자기 자신에 대한 힐도 동일하게 센다 |
| 저장 | `Unit.RoundEffectiveHealingDone` — **부여자**에게 누적된다 |
| 초기화 | 라운드 시작 시 0 |
| 산출 지점 | `Unit.ModifyHp` — 이미 `overheal`을 계산하고 있으므로 그 자리에서 `치유량 − 오버힐`을 더한다 |
| 사용처 | 프레이아 U `풍요의 산물`(광역 피해 배율)과 P `피톤치드`(아군 전체 STR). **같은 기록을 두 곳이 함께 쓴다** |

### 4-A.2 에어본

| 항목 | 내용 |
| --- | --- |
| 효과 | 지속시간 동안 **행동 불가**. 피격·대상 지정은 정상 |
| 지속 턴 | `1.5턴 × 시전자 CON ÷ 대상 CON`, **1~2턴으로 제한** |
| 재부여 | 남은 턴과 새 지속 턴 중 긴 쪽을 남긴다 |
| 면역 | `뿌리박기`(272) — 자신의 원소가 풀 또는 바위일 때 |
| 조회 | `Unit.IsAirborne` |
| 연계 | 쿠베라 P `대지의 계율`(에어본 적이 받는 피해 +10%), 스사노오 U `천총운검`(에어본 적을 즉시 벤다) |

CON 비교식이므로 **탱커가 탱커를 띄우면 오래 뜨지 않고, 후열을 띄우면 오래 뜬다.**
쿠베라가 CON 주스탯인 이유가 여기 있다.

### 4-A.2-B 기절

| 항목 | 내용 |
| --- | --- |
| 효과 | 지속시간 동안 **행동 불가**. 피격·대상 지정은 정상 |
| 지속 턴 | `1턴 × 시전자 CON ÷ 대상 CON`, **1~2턴으로 제한** |
| 재부여 | 남은 턴과 새 지속 턴 중 긴 쪽을 남긴다 |
| 면역 | 없음 |
| 출처 | 원소 반응 **진동**(바위 + 바위) — §6.3 |
| 구현 | `ControlStatuses.ApplyStun` |

에어본과 같은 CON 비교식이되 **기준이 1턴이라 한 턴을 넘기기 어렵다.**
빙결·에어본과 함께 `ControlStatuses`가 관리하는 '행동만 막는' 제어 계열이다.

### 4-A.2-C 제어 분쇄

**같은 대상에게 제어가 반복되면 지속시간이 줄고 결국 걸리지 않는다.**

| 회차 | 지속시간 배율 |
| --- | --- |
| 1회 | 100% |
| 2회 | 60% |
| 3회 | 30% |
| 4회 이상 | **면역** |

- 배율을 곱한 뒤 **반올림**하며, 0턴이 되면 아예 걸리지 않는다.
- 제어에 걸리지 않은 채 **자기 턴을 3번** 보내면 회차가 0으로 돌아간다.
- 회차는 **대상마다** 세며 누가 걸었는지는 보지 않는다.
- 라운드가 시작되면 초기화된다.

| 원래 지속 | 1회 | 2회 | 3회 | 4회 |
| ---: | ---: | ---: | ---: | ---: |
| 1턴 | 1 | 1 | 0 | 면역 |
| 2턴 | 2 | 1 | 1 | 면역 |
| 3턴 | 3 | 2 | 1 | 면역 |

전투가 자동이라 **플레이어에게 제어를 끊을 수단이 없다.** 바위 파티가 진동을 연달아 터뜨리거나
공허의 `폭풍`(1542)이 궁극기마다 전체 기절을 거는 식의 제어 루프는 되돌릴 방법이 없으므로
지속시간 쪽에서 상한을 건다. 모든 제어가 `ControlStatuses.ApplyControl` 한 곳을 지나므로
원소 반응·패시브·궁극기 어디서 왔든 같은 규칙을 받는다.

`빙결 면역`·`에어본 면역`처럼 **완전 면역이 먼저 판정**되고, 그다음 분쇄가 적용된다.

### 4-A.3 강인도

붕괴: 스타레일의 약점 게이지에 해당하는 **가상 체력**이다.

| 항목 | 내용 |
| --- | --- |
| 성질 | 체력과 **병렬**로 깎인다. 피해를 흡수하지 않으므로 실제 체력도 정상적으로 준다 |
| 감소 | 대상이 받은 실제 피해량만큼 감소 |
| 0 도달 | 강인도가 사라지고 **처치 판정 이벤트**가 발생한다 |
| 처치 판정 | `Unit.AnyUnitDied`와 공격자의 `OnKill`을 발행한다. 파죽지세·자기과신·순환 등이 그대로 반응한다 |
| **비포함** | 대상은 죽지 않는다. 골드·EXP·킬 카운트(`GameManager.OnKillEnemy`)는 발생하지 않는다 |
| 재부여 | 이미 강인도가 있는 대상에게는 새로 부여하지 않는다 |
| 조회 | `Unit.ToughnessCurr` / `Unit.HasToughness` |
| 부여 | 오르페우스 U `비탄의 연주` — `INT × 12` |

강인도는 **보호막과 반대 방향의 장치**다. 보호막은 피해를 막고, 강인도는 피해를 한 번 더 세어
처치 트리거를 앞당긴다. 그래서 적에게만 씌운다.

### 4-A.4 소환수

| 항목 | 내용 |
| --- | --- |
| 존재 형태 | 별도 `Unit`이 아니다. **칸을 차지하지 않는다**는 요구 때문에 소환자에 붙는 논리 객체로 구현한다 |
| 피해 산출 | 소환자의 지정 스탯 × 위력. **소환자의 `가하는 피해 증가` 버프는 적용되지 않는다** |
| 받는 버프 | `소환수 대상 버프`만 받는다. 현재는 `소환사`(265) +25% |
| 카운터 제외 | `n번째 공격마다` 계열은 소환수 공격을 세지 않는다 (`NormalAttack` 태그가 없으므로 자동으로 제외된다) |
| 태그 | `DamageTag.SummonAttack` + `DamageTag.AdditionalAttack` |
| 구현 | `Combat.Summons.Deal(...)`. `Unit.CalculateFinalDamage`가 `SummonAttack`을 보면 공격자의 `OutgoingDamageModifier`를 건너뛰고 `SummonDamageMultiplierModifier`만 적용한다 |
| 보유자 | 로키 P `펜리르`(제 DEX로 행동 + 표식 반응 물기), 바루나 U `마카라`(4턴 한시, 1턴마다) |
| 표식 반응 | 펜리르는 로키의 표식이 박힌 적이 아군에게 맞을 때 **추가행동**으로 한 번 더 문다. 방아쇠는 **아군 한 명당 한 번**이며 로키의 일반행동이 끝나면 되돌아온다. 로키와 펜리르 자신은 방아쇠가 되지 않으므로 한 주기의 상한은 넷이다 |

**소환사(73)는 필드 전체에 적용된다.** 로키가 필드에 있으면 바루나의 마카라도 강해진다.
같은 코드를 여럿이 들어도 중첩되지 않는다.

## 6. 원소

### 6.1 원소 종류

`None, Pyro, Hydro, Dendro, Anemo, Electro, Cryo, Geo, Void` — 8종 + 무속성

### 6.2 부착 규칙

| 항목 | 값 |
| --- | --- |
| 고유 원소 | 유닛 데이터의 `element`. 라운드 내내 유지되지만 **부착이 아니라 판정 전용이다** |
| 부착 지속 | **5턴** (`Unit.CommonElementAuraDuration`). 부착된 유닛의 턴으로 센다 |
| 근거 | 원신의 1U 오라 감쇠 시간 |
| 부여 | `GrantCombatElement(element, duration)` |
| 조회 | 조건 판정은 `HasCombatElement`, **반응 재료는 `HasAttachedElement`** |
| 초기화 | 라운드 시작/종료 시 `ResetCombatElements()` — 판정 축의 고유 원소만 남는다 |

#### 속성과 부착은 별개의 축이다

원신과 같은 모델이다. **유닛의 속성(고유 원소)은 원소 반응의 재료가 아니다.**
바위 유닛이라는 사실만으로 바위가 '부착'된 것은 아니며, 반응을 일으키려면
누군가 실제로 원소를 걸어 주어야 한다.

| 축 | 담는 곳 | 반응 재료 | 조회 |
| --- | --- | --- | --- |
| **고유 원소(속성)** | `_judgementElements` | ✕ | `HasCombatElement` |
| **부착 원소** | `_combatElements` | O | `HasCombatElement` · `HasAttachedElement` |

조건 판정(`원소 숙련`, `원소 친화` 등)은 두 축을 함께 보므로 속성만으로도 성립한다.
자기 속성과 같은 원소를 부착받아도 다른 원소와 똑같이 **지속시간이 붙는 일반 부착**이다.

### 6.3 원소 반응

두 원소가 한 유닛에게 겹치면 반응이 일어난다. **두 원소가 모두 소모되고** 결과가 남는다.
7원소 × 자기 조합 포함 **28쌍**이며, 공허는 반응에 참여하지 않는다.

#### 반응 행렬

|  | 불 | 물 | 풀 | 전기 | 얼음 | 바람 | 바위 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **불** | 화상 | 증발 | 연소 | 과부하 | 융해 | 확산 | 단조 |
| **물** | | 정수 | 개화 | 감전 | 빙결 | 확산 | 풍화 |
| **풀** | | | 착근 | 활성 | 휴면 | 확산 | 성장 |
| **전기** | | | | 축전 | 초전도 | 확산 | 접지 |
| **얼음** | | | | | 둔화 | 확산 | 경화 |
| **바람** | | | | | | 확산 | 확산 |
| **바위** | | | | | | | 진동 |

#### 세 가지 기본 규칙

| 규칙 | 내용 |
| --- | --- |
| **귀속** | 결과는 언제나 **원소가 부착된 유닛**이 가져간다. 버프도 마찬가지다 |
| **위력** | 전부 **유발자의 CON** 비례. CON은 최대 체력이자 **원소 친화력**이다 |
| **소모** | 참여한 두 부착 원소가 걷힌다. 속성(고유 원소)은 걷히지 않는다 |

버프 반응은 **자기 자신에게 원소를 둘러 만드는 것이 정규 운용**이다. 적에게 잘못 만들면
적을 이롭게 하고, 그것이 이 시스템의 상성이다. 보편적인 탱커는 STR을 주스탯으로 잡으므로
실질적으로는 **서포터가 반응을 키우는 자리**를 가져간다. CON이 높은 탱커(아누비스 등)에게는
원소 부착 수단을 주지 않는 것으로 균형을 잡는다.

#### 계열별 상세

**증폭 (3)** — 부착 직전에 들어간 그 공격을 되짚어 키운다. 세 반응의 계산 축은 같다.

| 조합 | 이름 | 효과 |
| --- | --- | --- |
| 불 + 물 | **증발** | `위력 40 × CON × 0.2` 고정 피해 + **그 공격 피해 × min(100%, CON × 0.5%)** |
| 불 + 풀 | **연소** | 〃 |
| 불 + 얼음 | **융해** | 〃 |

> 부착은 언제나 피해 **뒤**에 오므로(`TakeDamage` → `GrantCombatElement`), "이번 공격을 키운다"를
> 사후 추가 피해로 환산했다. 유발자가 **같은 대상에게** 방금 입힌 피해만 되짚는다
> (`Unit.LastResolvedDamage` / `LastResolvedTarget`). 피해가 없는 부착으로는 성립하지 않고
> 우선순위 2로 넘어간다.

**확산 (7)** — 바람의 전용 계열. 여섯 쌍은 **판정상 하나의 반응**이다.

| 조합 | 이름 | 효과 |
| --- | --- | --- |
| 바람 + 불/물/풀/전기/얼음/바위 | **확산** | **부착된 유닛과 같은 진영 전체**에 그 원소를 부여 |
| 바람 + 바람 | **확산** | 같은 진영 전체에 `위력 70 × CON × 0.2` 고정 피해 |

> **확산이 뿌린 부착은 다시 반응하지 않는다**(`GrantCombatElement(..., suppressReaction: true)`).
> 부착 지점이 곧 반응 지점이라 이 차단이 없으면 확산 → 반응 → 확산이 무한히 돈다.
>
> 진영은 **부착된 유닛 쪽**이다. 적에게 만들면 적 전체, 자신에게 만들면 아군 전체다.
> 바람 + 바람도 마찬가지라, 자기에게 바람을 두 번 두르면 **아군 전체가 맞는다.**

**버프 (5)** — 5스탯에 하나씩. 배율은 `min(30%, 유발자 CON × 0.2%)`, 3턴.

| 조합 | 이름 | 효과 |
| --- | --- | --- |
| 풀 + 바위 | **성장** | STR% 증가 |
| 불 + 바위 | **단조** | DEX% 증가 |
| 물 + 풀 | **개화** | CON% 증가 |
| 물 + 물 | **정수** | INT% 증가 |
| 전기 + 전기 | **축전** | LUK% 증가 |

> **차이식이 아니라 절대값**을 쓴다. `유발자 CON − 대상 CON` 꼴은 레벨이 오르면 양쪽이
> 함께 올라 언제나 0 근처를 맴돈다.

**디버프 (3)** — 같은 계수·같은 지속(3턴).

| 조합 | 이름 | 효과 |
| --- | --- | --- |
| 풀 + 전기 | **활성** | **특수** 태그 공격에게 받는 피해 증가 |
| 전기 + 얼음 | **초전도** | **물리** 태그 공격에게 받는 피해 증가 |
| 얼음 + 얼음 | **둔화** | DEX% 감소 |

**지속피해 (3)** — 2턴.

| 조합 | 이름 | 피해 | 터지는 시점 |
| --- | --- | --- | --- |
| 불 + 불 | **화상** | 대상 최대 체력의 5% | 대상 턴 시작 |
| 물 + 전기 | **감전** | `위력 90 × CON × 0.2` | 대상 턴 시작 |
| 물 + 바위 | **풍화** | `위력 90 × CON × 0.2` | **대상의 모든 행동 시작** |

> 풍화만 턴이 아니라 **행동**을 센다 — 일반행동·궁극기·추가행동 전부
> (`OnNormalActivates` · `OnUltimateActivates` · `OnAdditionalActivates`).
> 궁극기와 추가행동은 턴을 쓰지 않으므로 **빠르거나 궁극기·추가행동이 잦은 대상일수록 아프다** —
> 캐스터 보스와 추가행동 빌드의 대항 수단이다.
> 화상만 CON 명중 판정(`50% + (유발자 CON − 대상 CON) × 1%p`, 10~90%)을 거친다.

**제어 (3)**

| 조합 | 이름 | 효과 |
| --- | --- | --- |
| 물 + 얼음 | **빙결** | `0.75 + 유발자 CON × 0.01`턴 (1~3턴) 행동 불가 |
| 바위 + 바위 | **진동** | `유발자 CON ÷ 대상 CON`턴 (1~2턴) 기절 |
| 풀 + 풀 | **착근** | 다음 행동을 한 번의 행동에 필요한 AV의 **50%**만큼 뒤로 민다 |

**즉발 · 보호막 · 무효 (4)**

| 조합 | 이름 | 효과 |
| --- | --- | --- |

| 얼음 + 바위 | **경화** | `위력 100 × CON × 0.2` 보호막 |

| 풀 + 얼음 | **휴면** | 두 원소 소멸 |

#### 우선순위

여러 쌍이 동시에 성립하면 **하나만** 발동한다. 방금 부착된 원소가 반드시 참여해야 한다.

| 순위 | 계열 | 이유 |
| --- | --- | --- |
| 1 | 증폭 | 진행 중인 공격에 얹는다. 이번에 못 쓰면 사라진다 |
| 2 | 확산 | 원소를 퍼뜨려 다음 반응의 재료를 만든다 |
| 3 | 제어 | 판을 가장 크게 바꾼다. 분쇄·내부 쿨다운이 따로 누른다 |
| 4 | 즉발 피해 | |
| 5 | 지속피해 | 밀려도 다음 부착에서 다시 잡힌다 |
| 6 | 디버프 | |
| 7 | 버프 · 보호막 | 자기 부착으로 만드는 것이라 경합이 드물다 |
| 8 | 무효 | 다른 반응이 가능하면 굳이 고를 이유가 없다 |

동순위면 **남은 부착 지속시간이 가장 긴 원소**(= 가장 최근에 붙은 것)와 짝짓는다.
구현에서는 `ReactionKind`의 **선언 순서가 곧 우선순위**다.

#### 오사방지 — 아군이 아군에게 만든 해로운 반응

잔의 `오사방지`(104)를 든 유닛이 진영에 서 있으면, **같은 진영끼리 만든 해로운 반응**
(제어·즉발 피해·지속피해·디버프)이 발동하지 않는다. 버프·보호막·무효는 그대로 터진다.

버프 반응은 자기 진영에 원소를 둘러 만드는 것이 정규 운용인데, 그 과정에서 감전·과부하·초전도가
걸리면 **자동 전투라 되돌릴 수단이 없다.** 그 사고만 골라 지우는 장치다.
**적이 아군에게 건 반응은 막지 않는다** — 그건 상대의 정당한 수단이다.

부착 자체는 막지 않으므로 재료는 그대로 남고 반응만 쉰다.

#### 재부착 내부 쿨다운

같은 대상에서 **같은 반응**이 연달아 터지는 것을 막는다.

| 계열 | 간격 |
| --- | --- |
| 제어 | **3턴** |
| 지속피해 · 즉발 | **1턴** |
| 그 외 | 없음 |

**부착 자체는 막지 않는다.** 막으면 원소 숙련 코드(`X 원소를 보유한 적에게 +10%`)가
함께 꺼져 원소 딜러가 서로를 방해하게 된다. 반응만 쉬고 부착은 남는다.

간격은 **대상의 턴**으로 세며 라운드마다 초기화된다(`Unit.IsReactionReady`).

#### 같은 원소 반응

7쌍이 같은 원소끼리 일어난다(화상·정수·착근·축전·둔화·확산·진동).
**이미 붙어 있는 대상에게 한 번 더 부착**해야 성립하므로, 부착 집합만 봐서는 판별할 수 없다.
부착 지점(`Unit.GrantCombatElement`)이 *"이미 붙어 있었는가"* 를 반응 판정에 함께 넘긴다.

**속성이 바위인 유닛(오리온·쿠베라)은 첫 부착만으로는 진동에 걸리지 않는다.**
속성은 반응 재료가 아니므로 바위를 **두 번** 받아야 터진다.
덕분에 세이의 `창세`가 아군 전체에 바위를 둘러도 바위 아군이 기절하지 않는다.

#### 공통 규칙

| 규칙 | 내용 |
| --- | --- |
| 판정 시점 | `Unit.GrantCombatElement` — 부착 직후 한 번 |
| 중첩 | 지속피해는 `ExtendDuration`, 버프·디버프는 `Replace` |
| 알림 | `Unit.AnyElementalReaction` 이벤트 (야마 '고전압'이 이 신호를 듣는다) |
| 증폭 코드 | 스카디 `원소술사`(269) · 바루나 `대해의 판결`(274). 같은 계열이라 **가장 높은 하나만** |

**공허는 반응하지 않는다.** 부착할 원소가 없어서가 아니라 **의도된 설계**다.
공허 괴수와의 전쟁이 이 게임의 기본 컨셉이므로, 공허는 원소 판을 함께 굴리는 여덟 번째
원소가 아니라 **원소 바깥에 서 있는 것**이어야 한다. 공허 괴수의 기본형(무속성 변형)이
원소 빌드에 아무 재료도 내주지 않는 것도 같은 이유다.

🔸 **미구현** — 원소 간 상성표(가위바위보식 피해 증감)와 원소 저항은 아직 없다.

## 6-A. 전장 상태 (Field)

**유닛이 아니라 판 전체에 걸리는 것.** `Combat.Battlefield`가 한 번만 적어 두고
피해 계산이 그때그때 읽는다. 유닛 상태(`UnitStatus`)로 만들지 않은 이유는 대상이 유닛이 아니라서다 —
유닛마다 붙이면 도중에 소환·합류한 쪽이 빠지고, 걷을 때도 전원을 훑어야 한다.

| 항목 | 규칙 |
| --- | --- |
| 지속 | **깐 유닛의 턴**으로 센다. 그 유닛의 턴이 열릴 때마다 남은 턴이 준다 |
| 적용 | **양 진영 모두.** 판에 걸리는 것이라 적도 함께 받는다 |
| 판정 축 | **속성(고유 원소)**. 부착 원소가 아니다 |
| 초기화 | 라운드 종료 시 (`GridManager.OnRoundEnd`), 그리고 **깐 유닛이 쓰러졌을 때** |
| 적용 지점 | `Unit.CalculateFinalDamage`가 공격자 배율에 한 번 곱한다. 소환수 공격도 받는다 |

| 필드 | 거는 것 | 효과 |
| --- | --- | --- |
| **햇빛** `Sunlight` | 수리야 U `디바카르` (3턴) | 불 속성 +20% · 물·풀·얼음 속성 −20% |
| **눈** `Snow` | 볼바 `눈바라기`(1611) (3턴) · 토르 `노르드의 왕자`(1621) · **혹한의 노심**(1422) · **혹한의 동력로**(1432) (각 2턴, 자기 턴마다 갱신) | 얼음 속성 +20% · 불·풀 속성 −20% |

**눈은 햇빛의 거울이다.** 물을 약화 목록에서 뺀 것은 눈과 물이 서로를 방해할 이유가 없어서다.
같은 추위이고, 얼음+물 빙결이 이 필드에서 가장 잘 도는 반응이기도 하다.

**깐 유닛이 쓰러지면 판도 걷힌다.** 지속을 그 유닛의 턴으로 세기 때문에, 죽고 나면 남은 턴을
줄일 사람이 없어 라운드가 끝날 때까지 판이 남았다. 눈을 스스로 까는 혹한 계열이 들어오면서
**처치 순서에 값이 생겨야 했으므로** `Battlefield`가 읽는 자리에서 기준 유닛의 생존을 확인한다.

> 노르드 1은 이 대칭을 그대로 긴장으로 쓴다. 광전사가 불 속성이라 볼바가 깐 눈밭에서
> 피해가 20% 깎이는데, `설인`(1601)이 열리면 DEX가 두 배가 되어 그 손해를 속도로 되받는다.
> 두 코드가 같은 Lv50에 열리므로 **한 유닛 안에서 딜과 속도를 맞바꾸는 구조**가 된다.

> 🔸 츠쿠요미의 `만월`이 말하는 "밤 필드"는 아직 이 체계에 들어와 있지 않다.

### 6.x 부착 지속에 붙는 보정

부착은 `UnitStatus`가 아니라 `Unit`이 직접 들고 있는 타이머다. 그래서 상태 지속을 늘리는
`GrantedStatusDurationAdditiveModifier`로는 닿지 않고, 별도의
**`GrantedElementDurationAdditiveModifier(source)`** 가 받는다.

읽는 쪽은 **부착을 건 유닛**이다. 맞는 쪽이 아니라 거는 쪽이 오래 남기는 것이므로,
`Unit.GrantCombatElement`가 `source`의 효과를 훑어 합산한다. 지금 쓰는 것은
여덟 갈래 고리(423) 하나뿐이다.

## 7. 상태(Status) 시스템

`UnitStatus` + `BaseEffect` 단일 체계. (구 `StatusEffect` 딕셔너리 시스템은 제거됨)

### 7.1 UnitStatus 구성

| 요소 | 내용 |
| --- | --- |
| 식별 | 상태 ID + 문자열 Key |
| 시전자별 중첩 | Key에 시전자 ID를 포함시켜 구현 |
| 표시 | 이름, 설명 |
| 지속시간 | **0 이하 = 무한**, 라운드 종료 시 일괄 정리 |
| 카테고리 | `Positive` / `Negative` / `Neutral` |
| 중첩 정책 | 아래 7.2 |
| 효과 | `BaseEffect` 인스턴스 여럿 (팩토리 ID 또는 직접 생성) |
| 이로움 표식 | `IsBeneficial` → 부여 시 `OnBeneficialEffectReceived` 발행 |

### 7.2 중첩 정책 (`StatusStackPolicy`)

| 정책 | 동작 | 대표 사례 |
| --- | --- | --- |
| `Stack` | 독립적으로 중첩 | 맹독 |
| `ExtendDuration` | 기존 효과에 시간 추가 | 화상 |
| `ReplaceIfStronger` | 더 강한 것만 유지 | 방어 감소 |
| `Ignore` | 중복 무시, 기존 유지 | 일회성 표식 |
| `Replace` | 무조건 교체 (지속시간/수치 갱신) | 일반 버프 |

### 7.3 BaseEffect 훅

**생명주기 훅** — `OnApply` / `OnUpdate` / `OnRemove`

**스탯 질의 훅**

| 훅 | 개입 지점 |
| --- | --- |
| `CritChanceAdditiveModifier` | 치명타 확률 가산 |
| `CritMultiplierAdditiveModifier` | 치명타 피해 가산 |
| `OutgoingDamageModifier` | 주는 피해 배율 |
| `ReceivingDamageModifier` | 받는 피해 배율 |
| ~~`DefenseStatMultiplierModifier`~~ | 🔸 **사문화** — 방어력 폐지로 피해 계산에서 호출되지 않는다 |
| `PrimaryStatBonus` / `PrimaryStatMultiplier` | 5스탯 가산/배율 |
| `ManaRecoveryMultiplierModifier` | 마나 회복 배율 |
| `ShieldBonusAdditiveModifier` | 보호막 부여량 가산 |
| `ShieldReceivedMultiplierModifier` | 받는 보호막 배율 (수르트 `천상의 신체`) |
| `CodeAccelerationAdditive` | 코드 가속 가산 |
| `MaxHpMultiplier` | 최대 체력 배율 |
| `TryPreventDeath` | 사망 직전 개입 (체력 1로 생존) |

### 7.4 상태 정의 두 가지 방식

| 방식 | 용도 | 위치 |
| --- | --- | --- |
| 정식 상태 | 여러 코드가 공유하는 디버프(맹독/화상 등) | `UnitStatus.LoadStatusData()` ID 스위치 |
| 코드 정의 버프 | 특정 코드 전용 | `BuffStatus.Create(...)`, `Effects/Buffs/BuffEffects.cs` |

**버프 상태 ID 대역** (`BuffStatusIds`)

| 대역 | 용도 |
| --- | --- |
| 10~ | 공용 버프 |
| 100~199 | 유닛 고유 버프 |

### 7.5 상태 부여 예시

status.AddEffect(effectId, coefficient);

// 코드 정의 버프 (직접 생성한 효과 객체)

`BaseEnums.UnitEventType` — 리스너를 여러 개 등록할 수 있다.

| 이벤트 | 전달 인수 |
| --- | --- |
| `OnSpawn` | 자신 |
| `OnDeath` | 자신, 공격자 |
| `OnControlStarts` / `OnControlEnds` | 자신(, 공격자) |
| `OnPassiveActivates` / `OnNormalActivates` / `OnUltimateActivates` | 자신 |
| `OnTargeted` | 자신(=대상), 공격자 — **피해가 들어가기 전**, 대상이 확정된 순간 |
| `OnNormalAttackHit` | 자신, 대상, DamageContext |
| `OnBeneficialEffectReceived` / `OnBeneficialEffectGranted` | 자신, 상대 |

| `OnDamageDealt` | DamageResolvedContext (실제 가한 피해량 포함) |
| `OnStageStart` / `OnRoundStart` / `OnRoundEnd` / `OnStageEnd` | 자신 |

### 8.0 `OnTargeted` — 맞기 전에 끼어드는 자리

`Combat.Targeting.Announce`가 **대상이 확정된 직후, 피해 계산 전에** 발행한다.
지금은 일반행동 경로(`BaseNormalCode` · `NormalAttack`)에서만 나간다 — 궁극기는 코드마다
시전 흐름이 달라 공통 진입점이 없다.

| 축 | `OnAfterDamageTaken` | `OnTargeted` |
| --- | --- | --- |
| 시점 | 맞은 뒤 | **노려진 순간, 맞기 전** |
| 해결 | 추가행동 큐에 예약 | **그 자리에서 동기 해결** |
| 예 | 스카디 `북방의 수호자` | 잔 `최고의 방어` |

**큐에 예약하면 '먼저'가 되지 않는다.** 스케줄러는 진행 중인 행동이 끝나야 다음을 꺼내므로,
상대의 행동을 앞지르려면 공지를 받은 자리에서 곧바로 결판을 내야 한다.

`Announce`는 공지 도중 **공격자가 쓰러지면 false**를 돌려주고, 부른 쪽은 진행 중인 행동을
그대로 접는다. 잔이 되받아쳐 상대를 눕히면 그 상대의 공격은 아예 들어오지 않는다.

### 8.1 등록·해제 패턴

영구 효과를 거는 패시브는 **해제 조건을 함께 등록**한다.

```csharp
public override void CastCode()
{
    ApplyHolyEnchant();

    Action<(Unit, Unit)> onDeathHandler = null;
    onDeathHandler = (deathInfo) =>
    {
        StopCode();
        Caster.RemoveListener(BaseEnums.UnitEventType.OnDeath, onDeathHandler);
    };
    Caster.AddListener(BaseEnums.UnitEventType.OnDeath, onDeathHandler);
}
```

> **해제 트리거를 등록하지 않으면 상태가 영원히 지속된다.**

## 9. 라운드 시작/종료 처리

**라운드 시작** (`DefaultRoundStartEvent`)

2. `CastPassiveCode()` — 패시브 활성화

**라운드 종료** (`DefaultRoundEndEvent`)
1. `StatusController.ClearAll()` — 모든 상태 제거 (`OnRemove` 호출로 리스너 해제)
2. `ResetCombatElements()`
3. 보호막 초기화
4. 아군 필드를 전투 시작 시점 스냅샷으로 복원

### 10.1 현재 밸런스 실측

행동 직렬화로 전체 약 2.5행동/초, 일반행동 평균 위력 45(아군)/48(적)로 근사한 값이다.
아군 5인(세이·시·피그말리온·아탈란테·찬드라) 기준, **육성 강화는 제외**했다.

| 스테이지 | 편성 | 아군 Lv | 승리까지 | 전멸까지 | 여유율 |
| --- | --- | --- | --- | --- | --- |
| 1 | 일반 2기 | 1 | 10.3초 | 85.0초 | 12% |
| 3 | 일반 3기 | 4 | 13.4초 | 60.3초 | 22% |
| 4 | 마르켈루스(E) + 일반 | 5 | 17.0초 | 57.9초 | 29% |
| 6 | 일반 4기 | 8 | 16.3초 | 47.3초 | 34% |
| 7 | 일반 5기 | 9 | 22.0초 | 40.9초 | 54% |
| 8 | **사비나 — 중간 보스** | 11 | 20.0초 | 96.1초 | 21% |
| 9 | 필드 엘리트 + 일반 3기 | 12 | 24.2초 | 39.6초 | 61% |
| 10 | **스파르타쿠스 — 보스** | 13 | 29.8초 | 51.4초 | 58% |

여유율 = 승리까지 ÷ 전멸까지. 낮을수록 쉽다. 라운드 안에서 12% → 61%로 조여 오다가
보스에서 58%로 마무리되는 곡선이다. 전 구간이 60초 제한 안에 들어온다.

### 10.2 엘리트의 두 역할

같은 엘리트 등급이라도 출현 방식이 다르면 내구를 다르게 잡아야 한다.

| 적 | 역할 | 출현 | CON |
| --- | --- | --- | --- |
| 마르켈루스(2004) | **필드 엘리트** — 일반 적과 섞임 | 4·9스테이지 | 64 (+5/Lv) |
| 사비나(2005) | **중간 보스** — 단독 출현 | 8스테이지 | 105 (+15/Lv) |
| 스파르타쿠스(3003) | **보스** — 단독 출현 | 10스테이지 | 150 (+22/Lv) |

단독 출현하는 적은 아군 5인의 화력을 혼자 받아내므로 내구가 훨씬 높아야 한다.
**같은 적을 두 역할에 겹쳐 쓰면 한쪽이 반드시 망가진다** — 사비나를 9스테이지 편성에서 뺀 이유다.
