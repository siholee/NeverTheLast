## 2. 보상 코드 규칙

### 2.1 장착

| 항목 | 규칙 |
| --- | --- |
| 받는 쪽 | 보상 · 구매 시 아군 1명을 지정한다. 벤치 · 쓰러진 유닛도 받을 수 있다(소환수 제외, `RewardCodeFlow.Party`) |
| 슬롯 | **유닛당 활성 보상 코드 7칸 + 개수 제한 없는 개인 코드 보관함**(`Unit.RewardCodeSlotCount`). 고유 특성 · 일반행동 · 초월기는 칸을 쓰지 않는다 |
| 슬롯이 찰 때 | **초과분은 보관함으로 들어간다.** 기존 활성 코드를 지우거나 교체 대상으로 고르지 않는다 |
| 중복 | 보상/구매는 같은 유닛의 활성·보관을 모두 검사해 중복 획득을 막는다. 드래그로 같은 코드를 보관할 수 있지만 동시 활성화는 금지한다. 다른 유닛끼리는 활성 코드가 겹쳐도 된다. **상위를 이미 가진 유닛은 그 하위를 받지 않는다**(`Unit.CanReceiveRewardCode`) |
| 필드 효과 | "필드에 있으면"류는 보유자가 **필드에 서 있을 때만**(`Unit.IsOnField`) 켜진다. 여러 명이 들면 **높은 하나만** 적용한다(`RewardAura.Best`, 계열 키가 같은 오라끼리). 한 보유자의 코드 종료는 다른 활성 보유자의 공유 오라를 제거하지 않는다. 마지막 활성 보유자가 종료되면 제거한다. 죽는 중인 보유자는 오라에서 제외하며, 홀리 인챈트의 치명타 캐시는 사망 알림에서 즉시 갱신하여 자기 턴 이전의 추가행동·초월기에도 사라진 오라가 남지 않는다 |
| 수명 | 런 영구. 쓰러져도 남는다. 빈 칸을 포함한 활성 7칸은 `UnitSaveData.activeRewardCodeSlots`, 보관 순서는 `storedRewardCodeIds`에 저장한다(저장 v15, v12/v13/v14 자동 이관) — §7 |
| 장착 코드 위치 | **활성 코드만** `Unit.PassiveCodes`에 붙는 일반 `PassiveCode`다. 보관 코드는 스탯·상태·오라·정산 효과를 내지 않는다. 라운드 시작에 `CastPassiveCode`가 켜고, 라운드 종료에 `StopCode`가 상태 · 구독을 걷는다 |

**준비 중 무료 Drag & Drop.** Tab 창에서 활성 칸 → 보관함은 비활성화, 보관함 → 활성 칸은 활성화다.
점유된 활성 칸으로 옮기면 밀려난 코드는 출발 위치로 돌아가며 양쪽이 교환된다. 왼쪽 아군 초상화로 끌면 그 아군의
보관함으로 이동한다. 벤치·쓰러진 아군도 교환 대상이다. 출발 위치 변경·중복 활성·상하위 동시 활성·준비 밖 드롭은
양쪽 상태를 바꾸지 않는다. 전투 중에는 확인만 가능하다. `Combat.RewardCodeInventory`가 두 유닛의 결과를 먼저 검증한다.

**7칸은 활성 효과 예산이다.** 추가 코드 보유는 허용하지만 동시에 효과를 내는 수는 늘지 않는다. 보관과 무료 교환은
다음 적 편성에 맞춘 빌드 조정을 쉽게 만든다. 상점 가격·구매 2회·보상 티어 확률·코드 계수는 유지한다.
장비·중량·숙련은 복원하지 않는다. 아이템은 공용 보급, 보상 코드만 유닛별 보관함에 둔다.
장기 런에서 생존·경제·성장 코드를 전투별로 바꿀 수 있는 가치 증가는 별도 밸런스 시뮬레이션 대상이며 승률 검증을 완료했다고 보지 않는다.

### 2.3 상위 코드

- 하위 코드는 `SupersededByCodeId`로 상위를 가리킨다. 사다리의 원본은 `20_codes.yaml`의 `supersededBy`이고
  `RewardCodeCatalog`(`UpperOf` · `IsUpperOf` · `LowersOf` · `SealTargetOf`)가 조회한다. `Unit.CastPassiveCode`는 상위를 가진 하위의 발동을 재운다.
- **같은 유닛이 상위를 받으면 활성 하위는 보관하고 그 칸을 그대로 쓴다.** 상위를 받는 것은 칸을 더 쓰지 않는 강화다(`Unit.TryGrantRewardCode`가 하위를 보관하고 같은 자리에 상위를 넣는다).
- 옛 제도와 달리 **하위 없이도 상위를 받을 수 있다.** 무작위 보상에서 선행 조건을 걸면 상위가 사실상 나오지 않는다.
- 보상 화면은 파티 중 누군가 하위를 활성화하고 있으면 상위 카드에 `▲ 상위: ○○`을 표시한다.
- **T1 깡 스탯과 T2 퍼센트 스탯은 사다리가 아니다.** 합연산과 곱연산은 서로 다른 항이라 함께 들 때 각자 일한다.
  T2를 받아도 T1은 사라지지 않는다. 다만 **청동 승급의 인장**으로만 T1을 대응하는 T2로 바꿀 수 있다(아래 표).

### 2.4 승급의 인장

**인장은 올릴 수 있는 최대 티어로 나뉜다.** 한 번에 한 단계만 올리며, 높은 인장은 낮은 인장의 일을 모두 한다.
상위 코드가 없거나, 상위의 티어가 인장의 한계를 넘으면 쓸 수 없다.

| 인장 | 아이템 티어 | 최대 승급 | 쓰는 곳 |
| --- | ---: | ---: | --- |
| 청동 승급의 인장 | T2 | → T2 | T1 깡 스탯 → 대응 T2 |
| 은 승급의 인장 | T3 | → T3 | 소환술사 → 소환사 · 결전의 포효 → 결전의 일격 · 연격 → 연환격 · 되받아치기 → 응징 · 기수 → 도발의 문장 |
| 금 승급의 인장 | T4 | → T4 | 재기의 바람 → 기사회생 · 투사 → 하루종일도 할 수 있어 · 치유의 손길 → 의신의 가호 · 역병의 저주 → 죽음의 계약 · 원소 촉매 → 원소술사 · 축적의 촉진 → 겹겹이 쌓인 운명 |
| 별빛 승급의 인장 | T5 | → T5 | 기사회생 → 완벽한 재기 · 천살성 → 당연한 운명 · 원소술사 → 대해의 판결 |

인장은 활성·보관 코드에 모두 쓸 수 있다. 재료 코드를 변환하는 승급이므로 하위는 사라지고 상위가 **같은 활성 칸 또는 보관 위치**에 들어간다 — `Unit.TryReplaceRewardCode`.
같은 코드가 여러 장이면 활성·보관 위치와 축전기 저장량을 보고 한 장을 선택한다. 선택지는 8장씩 페이지로 나누고 취득층도 표시하며, 선택한 인스턴스의 GUID·저장량·취득 스테이지를 보존한다. 게임 API도 승급 사다리 및 조화의 문장 허용 목록을 검증한다.
인장은 인벤토리에서 준비 페이즈에만 쓴다 — 아군 → 올릴 코드 → (조화의 문장이면) 바꿀 T2 순으로 고른다(`RewardCodeFlow.StartSeal`, `GameManager.UseSeal`).
이미 대응 T2를 가진 유닛의 T1은 올릴 수 없고, 인장의 최대 티어를 넘는 상위도 못 올린다.

## 3. 코드 태그

**유닛의 `archetypeTags`와 같은 키를 쓴다.** 코드 카드의 태그 칩이 유닛 카드의 태그 칩과 같은 아이콘이므로
"이 태그를 가진 유닛에게 주면 된다"가 그림으로 읽힌다. 한 코드에 태그는 1~2개.

| 키 | 표시 | 코드에서의 뜻 | 신규 |
| --- | --- | --- | :-: |
| `Universal` | **범용** | 누구에게 줘도 손해가 없다. 기본 스탯 · 생존 | ✔ |
| `Economy` | **경제** | 전투 밖 자원(골드 · EXP)을 늘린다 | ✔ |
| `Burst` | 방출 | 마나 효율 · 궁극기 피해. 방출 유닛(초월기가 핵심인 유닛)이 잘 받는다 | |
| `Precision` | 정밀 | 치명타 · 처형 · 단일 피해 조건 | |
| `FollowUp` | 연속 | 추가행동 | |
| `Swift` | 신속 | 속도 · 행동 빈도 | |
| `Support` | 지원 | 필드 오라 · 아군에게 주는 효과 | |
| `Control` | 제어 | 행동불능 대상 | |
| `Healing` | 치유 | 회복 | |
| `Shielding` | 방어 | 보호막 | |
| `Infusion` | 부여 | 원소 부착 · 원소 반응 | |
| `Sturdy` | 견고 | 방어 · 전열 · 대상 지정 | |
| `Counter` | 반격 | 반격 피해 | |
| `Summon` | 소환 | 소환수(피그말리온 포함) | |
| `Domination` | 지배 | 지속피해 · 해로운 상태 · 특수공격력 | |
| `Indomitable` | 불굴 | 체력을 자원으로 쓰거나 위기에서 강해진다 | |
| `Growth` | **성장** | 런 내내 쌓이는 **영구 중첩**을 늘린다 — [Detail_03 §3.1](Detail_03_Character.md) | ✔ (유닛 태그도 신설) |

키와 표시 이름의 원본은 `UnitTagCatalog`다(`Universal` · `Economy` · `Growth`를 이 체계에서 더했다). 코드의 태그는
`20_codes.yaml`의 `codeTags`에 적는다.

### 3.1 공격 형태

`Code.AttackForm`과 DamageTag의 50000번대는 베기·찌르기·사격·타격·주문이다. 접촉 여부와 소환 피해 표지는 별개다.
지속/반응/덧붙는 피해를 직접 공격 형태로 세지 않는다. `requiresAttackForm` 후보 제한은 실제 파티의 공격 선언을 조회한다.
상세 판정은 [02 전투](Detail_02_Combat.md)와 `Combat/AttackForms.cs`를 따른다.

## 5. 보상 풀과 상점

### 5.1 보상 카드 한 장의 생성

`RewardManager.GenerateRewards(count, round, killedEnemyIds)`가 선택지를 만든다. 카드 장수는 기본 3장, 25스테이지마다 +1, 최대 6장이다.
분류 비율과 태그 · 상위 가중치의 원본은 `90_rewards.yaml`(`rewardCategoryWeights` · `codeTagWeights` · `upperCodeWeight`)이다.

```
카드 한 장마다
1. 라운드 티어 확률로 티어를 굴린다                         (Detail_13 §2, 현행 그대로)
2. 분류를 굴린다:  코드 55 · 소모품 30 · 적 드랍(식량 등) 15
3. 그 분류 · 그 티어의 후보 중에서 가중치로 고른다
     코드  — 태그 가중치: 파티 유닛 태그와 겹침 ×2 · 범용 ×1 · 그 밖 ×0.5, 상위 가중치 ×1.5
     소모품 — 써서 달라지는 것만(다친 아군이 없으면 치료 제외, 쓰러진 아군이 없으면 부활 제외)
     드랍  — 이번 전투에서 처치한 적의 드랍표 + 공용 드랍
4. 후보가 없으면 같은 티어의 다른 분류(무작위 순) → 가까운 티어(전 분류) 순으로 물러난다
선택지가 다 차면
5. 코드가 한 장도 없고 코드 후보가 남아 있으면, 무작위 한 장을 가까운 티어의 코드로 바꾼다
```

| 분류 | 후보 |
| --- | --- |
| 코드 | 구현된 보상 코드(`RewardCodeFactory.IsImplemented`) 중 아래 후보 조건을 통과한 것 |
| 소모품 | `90_rewards.yaml`의 즉시 소모품(치료 · 부활 · 사탕 · 운명의 주사위 · 경험의 서 · 휴식의 향로 · 경험의 서 상권) + `40_items.yaml`에서 `rewardPool: true`인 비약 · 승급의 인장 · 넥타르 |
| 적 드랍 | `commonDropItemIds`(식량) + 처치한 적의 `drops`. 식량 · 귀중품 |

| 규칙 | 값 |
| --- | --- |
| 코드 보장 | 한 번의 보상 선택지 중 **최소 1장은 코드** (5단계) |
| 같은 선택지 안 중복 | 금지 (뽑힌 카드는 모든 분류의 풀에서 지운다) |
| 줄 곳이 없는 코드 | 파티 전원이 이미 가진 코드(또는 그 상위)는 후보에서 뺀다(`Unit.CanReceiveRewardCode`) |
| 대상이 없는 코드 | 공격 형태 코드는 그 형태 공격 보유자가, 성장 코드는 `Growth` 유닛이 파티에 있을 때만 후보 |
| 상위 코드 | 파티 누군가 하위를 갖고 있으면 가중치 ×1.5 |
| 리롤 | 보상 화면의 **다시 굴리기** 버튼이 리롤 티켓 1장을 쓰고 같은 장수로 선택지를 새로 만든다(`RewardManager.RerollRewards`). 티켓이 없으면 버튼이 숨는다. 처치 기록은 그대로 쓴다 — §6.2 운명의 주사위 |

> 태그 가중치가 시뮬레이션 우주의 "운명의 길" 역할을 한다. 파티 태그가 빌드 방향을 끌어당기지만
> 겹치지 않는 코드도 0.5로 남겨 빌드를 갈아탈 여지를 둔다.

**실측(하네스 `r12_core`, 라운드 5 · 3장 · 300세트):** 카드 분류 비율이 코드 약 62% · 소모품 약 29% · 드랍 약 7%였다. 굴린 비율(55 · 30 · 15)보다 코드가
높은 데에는 **최소 1장 코드 보장**도 작용한다. 모든 분류에 같은 티어 후보가 충분하다고 가정해도 3장 세트의 보장만으로 코드의 기대 비중은
`0.55 + 0.45³ / 3 = 약 58.0%`다. 드랍이 낮아지는 추가 원인은 후보가 없는 분류에서 다른 분류로 물러나는 규칙이다
(현재 드랍 식량은 T1~T2에만 있어, T3 이상을 굴리면 드랍이 물러난다).
모든 세트에 코드가 1장 이상 들어갔다. 티어별 후보 수가 적은 분류의 비율은 밸런싱 때 다시 본다.

### 5.2 상점 고정 재고

**고정으로 파는 것은 "없으면 런이 무너지는데 운에 맡기면 안 되는 것"뿐이다.** 화력 코드는 팔지 않는다.

상점 탭은 **코드 · 회복·성장 · 공용 보급 · 판매** 넷이다. **코드 탭으로 시작**한다.
공용 보급은 식량과 정화의 성수를 함께 다루므로 식량 전용으로 표시하지 않는다. 긴 목록은 스크롤로 모든 상품에 접근한다.

| 탭 | 품목 | 기본가 | 근거 |
| --- | --- | ---: | --- |
| 회복·성장 | `90_rewards.yaml`에서 `goldCost`가 있는 즉시 소모품 **11종** — 치료의 영역 T1~T4 · 엘릭서 · 부활의 신약 T1~T3 · 에테르 · 이상한 사탕 2종 (§6.2 "기존") | 현행 | 신규 즉시 소모품(운명의 주사위 · 경험의 서 · 휴식의 향로 · 경험의 서 상권)은 `goldCost`가 없어 상점에서 팔지 않는다 |
| 공용 보급 | `40_items.yaml`에서 `shopPrice`가 있는 아이템 — 식량 3종 + **정화의 성수**(T2, 기본가 100) | 현행 · 100 | 식량은 긴 휴식의 재료, 성수는 다음 전투의 해로운 상태 1회 대응 수단이다 |
| **코드** | **재기의 바람**(701) · **정신력**(702) · **자가치유**(703) (T3) | 300 | 생존 · 제어 저항 · 지속 회복. 치유 담당이 없는 현 로스터의 구멍. `20_codes.yaml`의 `shopFixed` + `shopPrice` |
| 판매 | 판매가가 있는 공용 아이템 | — | 구매 한도를 쓰지 않는다 |

- 상점에 오르는 전투 비약은 정화의 성수뿐이다. 비약 · 인장의 §6.2 "기본가"는 상점이 아니라 **보상 풀에서만** 나오는 품목이라 현재 쓰이지 않는다(`shopPrice` 없음).
- 가격은 현행처럼 `기본가 × 현재 스테이지`, 구매는 준비 페이즈당 2회(`GameManager.MaxShopPurchases`)를 공유한다.
- 코드 탭은 산 자리에서 대상 선택기를 연다(`RewardCodeFlow.StartReceive`). 칸이 찼으면 버릴 코드를 고른다. **골드는 마지막에 확정**하고, 적용이 실패하면
  값을 돌려준다. 받을 아군이 없는 코드는 "받을 아군 없음"으로 막는다. 구현이 없는 코드는 진열하지 않는다.
- 상점 코드는 T3 회복약(고급 치료의 영역 250)보다 조금 비싸게 잡는다. 한 번 쓰고 끝나는 약보다 비싸되,
  보상으로 얻는 쪽이 늘 이득이어야 보상 선택이 의미 있다.

## 9. 축전기 — 코드별 저장량

**축전기 24종.** 현행 전체 개수는 §4를 따른다. 저급 T1(540~547) → 중급 T2(640~647) → 고급 T3(740~747) 사다리다. 처음 저장량은 0이고, 활성 보유자가 살아서 필드에 있을 때 필드 유닛 사망마다 +1, 소환수 사망마다 +0.25를 충전한다. 보유자 자신의 사망·벤치 사망·라운드 종료 소환수 정리는 충전하지 않는다. 중첩 획득량 ×1.5/×2 코드가 한 번 적용된다.

| 접미 이름 | 저급/중급/고급 ID | 저장량 1당 증가 | 저급 최대(12) | 중급 최대(24) | 고급 최대(48) |

저급의 최대값은 기존 T1 즉시 스탯 코드와 비슷하거나 작다. 충전 전의 빈 칸과 전장 생존 조건을 대가로, 같은 한 장을 인장으로 강화해 더 높은 상한을 연다. 성장 유닛이 없어도 모든 편성에서 등장하고, 보관 중에는 스탯·충전 모두 멈춘다. 상위 코드의 보상·구매는 새 한 장(0충전)을 얻고 하위를 보관하는 기존 규칙을 따른다. **인장 승급은 같은 한 장을 변환하므로 저장량·취득 스테이지를 유지한다.**

저장량은 유닛의 공통 영구 중첩이 아니라 **코드 한 장의 인스턴스**에 속한다. 활성·보관 전환, 아군 간 교환, 동일 코드끼리 교환, 런 저장·복원에서도 인스턴스 ID와 값이 함께 움직인다. 한 유닛이 같은 코드를 활성·보관에 각각 가지고 있어도 저장량은 독립적이다. 수치 원본은 `20_codes.yaml`의 `capacitorStat/PerCharge/Cap`이다.

판매는 상점 판매 탭에서 한 장씩 한다. `기본 판매가 × 취득 스테이지 × (1 + 저장량/상한)`이며 기본 판매가는 상점 코드의 기본 구매가 25%, 그 밖에는 `20 × 2^(티어−1)`이다. 완충 가격은 빈 코드의 2배다. 취득 시세를 고정해 후반 스테이지·무료 교환으로 판매가를 늘리는 경로를 막는다. 판매는 구매 횟수를 쓰지 않으며 **귀중품 전부 팔기**는 코드를 팔지 않는다.

개별 코드 저장은 v14에서 도입했다. 현재 형식 **v15**도 기존 활성/보관 ID 배열과 `activeRewardCodeInstances`, `storedRewardCodeInstances`의 `codeId/instanceId/charge/acquiredStage`, `nectarStats`를 보존한다. v12·v13은 코드에 0충전 새 식별자를 부여해 복원한다. v14→v15는 10라운드 테마 진행을 8라운드로 옮기며 코드 인스턴스·축전량·넥타르를 변경하지 않는다. 전투 전후 스냅샷도 같은 DTO를 쓴다.

보상 풀·상점은 `RewardCodeCatalog`·`RewardCodeFactory`의 현행 데이터 기반 경로에 등록한다. 신규 코드들은 상점 고정 후보에도 등록한다.
