## 2. 페이즈 타이머

| 항목 | 값 | 코드 |
| --- | --- | --- |
| 준비 시간 | **30초** | `GameManager.preparationTime` |
| 전투 제한 | **전역 80턴** | `GameManager.roundTurnLimit` |

전투 제한은 초가 아니라 **턴 수**다. 전투가 턴제이므로 초로 재면 연출 길이가
라운드당 행동 수를 좌우한다. 추가행동·패시브 발동은 턴으로 세지 않는다.

- HUD의 원형 게이지는 `PhaseProgressRatio`(1 → 0)를 읽는다. 숫자는 준비 단계에서 남은 초, 전투 중에는 남은 턴(`80T` 형태)이다.
- 타이머가 돌지 않는 페이즈에서는 비율 `1`, 남은 초 `0`을 반환한다.

## 3. 준비 페이즈

준비 페이즈에서 할 수 있는 것은 **상점 · 휴식 · 공용 인벤토리 · 덱 구성**뿐이다.
추가 전투와 장비 화면은 없다. 보스 스테이지도 같은 준비 기능을 쓴다.

| 기능 | 규칙 | 메서드 |
| --- | --- | --- |
| 상점 | 준비 페이즈당 구매 2회 | `OpenShopFromPreparation()` |
| 휴식 | 준비 페이즈당 한 번, 짧은/긴 휴식 중 선택 | `OpenRestFromPreparation()` |
| 공용 인벤토리 | 파티가 공유하는 아이템과 식량 확인 | `OpenInventoryFromPreparation()` |
| 덱 구성 | 필드·대기석 배치 변경 | `OpenDeckSetupFromPreparation()` |

짧은 휴식은 살아 있는 아군의 최대 체력 50%를 회복하고 횟수 1을 쓴다. 긴 휴식은 식량 40을
소비해 전원을 부활·완전 회복하고 짧은 휴식 횟수를 2로 복원한다. 수치 원본은
[Detail_05 §3](Detail_05_Economy.md)이다.

**패배해도 같은 스테이지를 재도전하지 않는다.** 승패는 해당 스테이지의 확정 결과이며,
패배하면 클리어 보상 없이 다음 스테이지 준비로 넘어간다. 따라서 보스전의 준비 행동 잠금도
한 번의 전투에만 적용된다.


## 4. 스테이지와 라운드

| 값 | 계산식 |
| --- | --- |
| 라운드 | `Round = ((Stage - 1) / 10) + 1` |
| 라운드 내 위치 | `StageInRound = ((Stage - 1) % 10) + 1` |
| 적 레벨 | `EnemyLevel = Stage` (1스테이지 = Lv.1 = 성장분 0) |

**1라운드 = 10스테이지 = 테마 1개.** 테마는 라운드가 바뀔 때마다 **균등 추첨**으로 뽑는다.
`enabled: false`인 테마는 `RoundManager.ActiveThemes()`가 걸러 내므로 추첨표에 들어가지 않는다.

### 4.1 테마 추첨 — 연작과 확률

추첨은 균등하다. 확률을 조절하는 장치는 가중치가 아니라 **치환**이다.

| 필드 | 뜻 |
| --- | --- |
| `rotationRedirectThemeId` | 이 테마가 뽑히면 **대신 시작할** 테마. 0이면 자기 자신 |
| `chainNextThemeId` | 이 테마의 라운드가 끝나면 **추첨 없이** 이어질 테마. 0이면 다시 추첨 |

연작 테마(옛 노르드 3부작)가 이 구조를 쓴다. 세 편 모두 추첨표에 들어가되 2 · 3편이 뽑히면 1편으로 치환되므로,
균등 추첨을 유지한 채 1편의 등장 확률만 세 배가 된다. 🔸 지금은 시험장 하나라 쓰는 테마가 없다.

> 추첨은 라운드마다 한 번이다. 뽑은 결과는 `RoundManager._themeDecidedForRound`에 묶여 있고
> 저장에도 들어간다. 그러지 않으면 같은 라운드 안에서 스테이지를 넘길 때마다,
> 또 저장을 불러올 때마다 주사위가 다시 굴러 테마가 갈린다.
>
> 🔸 직전 라운드와 같은 테마가 연속으로 나올 수 있다.
> 균등 추첨의 의도된 결과다. 막으려면 직전 테마를 추첨표에서 빼는 규칙을 추가해야 한다.

## 5. 스테이지 슬롯 배치

아래 표의 슬롯 번호는 **내용 슬롯**이다. 고정 보스가 없는 평범한 라운드에서는 스테이지 번호와 같다.

| 내용 슬롯 | 콘텐츠 | 판정 |
| --- | --- | --- |
| 1, 2, 3, 4, 6, 7 | 일반 전투 | 테마 `stagePatterns` |
| **5** | **사건 스테이지** | 내용 슬롯 5, 고정 보스 스테이지가 아닐 것 |
| **중간 보스** | 테마의 `midBossStageInRound` (기본 **8**) | `_currentStageTheme.midBossId` |
| 9 | 일반 전투 — 단, **고정 보스 라운드에서는 테마 보스** | 내용 슬롯 10 |
| **10** | 테마 보스 (고정 보스 라운드에서는 고정 보스) | 내용 슬롯 10 / `fixedBossStages` |

> **테마가 그 슬롯의 `stagePatterns`를 정의하면 중간 보스·보스 단독 스폰보다 우선한다.**
> 보스에게 호위를 붙이려면 패턴에 보스 ID를 직접 적는다.

### 고정 보스 (`fixedBossStages`)

**데이터는 현재 비어 있다 (`fixedBossStages: []`).**
25/50/75/100 지점에 무엇을 세울지는 아직 정해지지 않았다.
(개편 전에는 네 지점 모두 오딘(3001)이었으나, 노르드 테마 제거와 함께 사라졌다.)

**슬롯 규칙은 구현되어 있다.** 고정 보스가 낀 라운드는 **2번 슬롯을 건너뛰고 이후를 1씩 당긴다.**

```
평소       1  2  3  4  5(사건) 6  7  8  9  10(보스)
고정 보스  1  3  4  5(사건)    6  7  8  9  10(보스)  고정 보스
```

결과적으로 테마 보스가 9번째 전투로 당겨지고 마지막 칸이 고정 보스 자리가 된다.
편성·사건·보스 판정은 스테이지 번호가 아니라 이 **내용 슬롯**(`RoundManager.ContentSlotInRound`)을 본다.

## 6. 적 편성

### 6.1 편성 방식 두 가지

테마의 `stagePatterns[].patterns[]`는 두 형태 중 하나를 쓴다.

**명시 편성** — 적 ID를 직접 나열

```yaml
- stageInRound: 2
  patterns:
    - { enemyIds: [1010, 1012, 1011], weight: 50 }
    - { enemyIds: [1010, 1013, 1015], weight: 50 }
```

**분류 편성** — 분류(archetype)만 지정, 해당 `themeId`의 적 중에서 무작위 선택

```yaml
- stageInRound: 3
  patterns:
    - { archetypes: [7, 7, 10], weight: 50 }
    - { archetypes: [8, 8, 10], weight: 50 }
```

**열 고정 편성** — 전열·후열을 직접 나눠 적는다

```yaml
- stageInRound: 1
  patterns:
    - { frontIds: [1062, 1062], rearIds: [1062, 1062, 1062], weight: 100 }
```

`enemyIds`는 적의 `archetype`이 열을 정하므로 **같은 병종을 두 열에 나눠 세울 수 없다.**
`frontIds`·`rearIds` 중 하나라도 적혀 있으면 `enemyIds`·`archetypes`는 무시된다.

패턴은 `weight` 가중 추첨으로 뽑는다.

| 테마 | 사용 방식 |
| --- | --- |
| 공허의 시험장 (1) | 열 고정 편성(`frontIds` / `rearIds`). 사건 슬롯 5를 제외한 전투 슬롯 전부 정의 |

시험장이 `stagePatterns`를 모두 채우고 있으므로, `70_rounds.yaml`의 라운드 타입은 사실상 폴백으로만 남아 있다.

### 6.2 분류(archetype)별 배치 열

7·8·9는 전열, 그 외는 후열이다. 한 열은 최대 4칸이며 **넘치는 적은 배치되지 않는다**
(예전에는 조용히 사라졌지만 지금은 경고를 남긴다). 열 고정 편성은 이 판정을 건너뛴다.
적별 분류는 [Detail_09 §2](Detail_09_Enemy_Catalog.md)에서 관리한다.

새 분류 ID를 추가하면 `RoundManager.GetColumnForArchetype()`도 함께 갱신한다.

### 6.3 라운드 타입 (`70_rounds.yaml`)

테마가 `stagePatterns`를 정의하면 그쪽이 우선하므로, 현재는 폴백 역할만 한다.
사용 가능한 archetype이 7~10으로 줄어 전 항목이 그 범위로 재작성되었다.

| ID | 성격 | 편성 |
| --- | --- | --- |
| 1, 3, 9 | 일반 | 전열 중심 2~5기 |
| 2, 5, 6 | 일반 | 후열 혼합 2~4기 |
| 7 | 일반 | 전열 집중 3~5기 |
| 4 | **엘리트** | `2004` 또는 `2004+2005` |
| 8 | **엘리트** | `2004+2005` 또는 `2004+2004+2005` |
| 10 | **보스** | `3003` |

> 엘리트 · 보스 ID(2004 · 2005 · 3003)는 옛 로스터의 것이라 지금은 없다. `RoundManager.ResolveFallbackEnemy`가
> 현재 테마의 같은 등급 적으로 바꿔 끼우므로 동작에는 문제가 없다.

## 10. 라운드 종료 정산

1. 남은 적 수만큼 생명력 차감
2. 전투 종료 시점의 **체력 · 궁극기 자원 · 생사**를 전투 전 스냅샷에 덮어쓰기 (`CaptureAllyBattleState`)
3. **아군 필드를 그 스냅샷으로 복원** (`SaveAllyFieldState` / `RestoreAllyFieldState`)
4. 모든 상태 정리 (`StatusController.ClearAll`), 보호막·원소 부착·고유 전투 자원 초기화
5. 생명력 판정 → 승리면 보상, 패배면 보상 없이 다음 스테이지, 0이면 게임 오버

### 무엇이 전투를 넘어가는가

| 넘어간다 | 넘어가지 않는다 |
| --- | --- |
| **현재 체력** | 상태이상·버프·디버프 (`StatusController.ClearAll`) |
| **궁극기 자원**(마나·중첩) | 보호막 · 집중 |
| **생사** — 쓰러진 아군은 쓰러진 채로 남는다 | 원소 부착 |
| 레벨·EXP·공용 인벤토리 | 고유 전투 자원(중첩형 코드의 스택 — 세이의 창세의 결정 포함) |

> 🔸 **0.4.9에서 바뀐 규칙이다.** 예전에는 3번이 <b>전투 시작 시점</b> 스냅샷으로 되돌려
> 깎인 체력이 매 전투 원상복구되고 쓰러진 아군까지 만피로 되살아났다. 그래서 회복약과
> 부활약이 존재할 이유가 없었다. 지금은 전투가 끝난 상태 그대로 다음 전투로 넘어간다.
>
> 쓰러진 아군은 **자기 칸을 계속 점유한 채** 비활성으로 남아 `RewardManager.IsValidReviveTarget`의
> 대상이 된다. 칸을 풀어 주면 그 자리에 다른 아군이 들어와 스냅샷에 같은 좌표가 두 줄 생기고,
> 다음 복원에서 스폰이 충돌해 살아 있던 아군까지 유실된다(`LayDownRestoredAlly`).
> 부활 수단이 없으면 그 런 동안 계속 빠진 채로 간다.
>
> **전원이 쓰러진 채로 전투가 시작되면 그 자리에서 런이 끝난다.** 이길 방법이 없는데 그대로 두면
> 스테이지마다 즉시 패배가 반복되며 생명력만 깎이기 때문이다 — 전투 시작 파티가 비어 있으면
> 생명력을 0으로 내려 기존 게임 오버 경로를 탄다.

궁극기 자원은 승리·패배와 관계없이 다음 전투 및 저장/불러오기에 유지된다.
단, `1-10 → 2-1`처럼 라운드(테마)가 바뀌는 스테이지 전진에서는 파티 전원의 자원을 0으로 초기화한다.

## 11. 게임 모드 — 무한 모드 하나

**게임 모드는 무한 모드 하나다.** 옛 육성 모드(메인 1 + 서포트 4, 100스테이지 완주)와 `GameMode` 구분은 사라졌다.
메인 메뉴의 `새로운 여정`이 곧 무한 모드다.

| 항목 | 값 |
| --- | --- |
| 편성 | **해금한 캐릭터 1~5명** (`CharacterSelectionManager.MaxSelection` / `MinSelection`), 중복 불가 |
| 메인 · 서포트 | 없다. 편성 첫 자리는 **대표**로, 준비 화면 레벨 표기 · 추천 조합 기준에만 쓴다 |
| 스테이지 상한 | 없다. 라운드가 바뀌면 테마를 다시 뽑고 적 레벨이 계속 오른다 |
| 보상 확률 | 현재 라운드 행, 10라운드 이후 10라운드 행 고정 — [Detail_13 §3](Detail_13_Reward_Catalog.md) |
| 보스전 준비 | 일반 스테이지와 같은 상점 · 휴식 · 인벤토리 · 덱 구성 |
| 종료 | 생명력 0(게임 오버) 또는 라운드 데이터 소진 |

### 스테이지 전진 단일 진입점

`RunManager.AdvanceToNextStage()` — 보상/사건 어느 흐름에서 오든 여기를 통과한다.

```
다음 라운드 로드 실패 → RunComplete (세이브 삭제 → 메인 메뉴)
그 외                 → 테마가 바뀌었으면 마나 초기화 → 세이브 → 다음 스테이지 진입
```

## 12. 캐릭터 편성 자격

캐릭터는 **해금 / 미해금**으로만 나뉜다(`characterType: Unlocked | Locked`, 판정 `CharacterSelectionManager.IsUnlocked`).
해금 경로는 영입 사건 · 계정 해금(`SaveSystem.AddStarterUnlock`)이다. 현재 로스터는 세이·시 2명(모두 Unlocked).

## 13. 난이도 곡선 설계

| 축 | 상승 방식 |
| --- | --- |
| 적 강화 | 스테이지당 레벨 +1 (`EnemyLevel = Stage`). 성장 가속은 없다 |
| 아군 강화 | EXP 레벨업 + 코드 효과 |
| 스파이크 | 중간 보스(8스테이지) → 10스테이지 보스 |
| 체크포인트 | 없음 (고정 보스 미설정) |

🔸 훈련이 빠져 아군 레벨이 적 레벨을 따라가는지 아직 재지 않았다. 개편 뒤 밸런스 실측은 없다 — [Design_Backlog](Design_Backlog.md).

### 13.1 테마 사이의 무게는 같아야 한다

**테마는 라운드마다 무작위로 뽑히고 적 레벨은 스테이지가 정한다.** 그래서 어느 테마가 나오든
같은 라운드의 무게는 비슷해야 한다 — 테마별 난이도 편차는 설계가 아니라 데이터 흔들림이다.

🔸 기준 유닛(옛 오딘)이 사라졌다. 새 테마가 둘 이상 들어오면 기준을 다시 세운다. 원칙 — 같은 라운드의 무게는 어느 테마든 비슷해야 하고, 체력은 테마 단위로 같은 배율을 먹여 내부 비율을 지킨다.
