### 1.5 TAB 화면 (CodexScreen)

발더스 게이트 3 인벤토리 화면을 레퍼런스로 삼는다.

```
┌───────────────────────────────────────────────────────────┐
│  캐릭터명                              중량            ✕   │
├──────────┬──────────────────────────────┬─────────────────┤
│ 파티 목록 │ [장비][코드][시트][추천 조합] │  선택 항목 상세  │
│          ├──────────────────────────────┤                 │
│  캐릭터1  │ STR  DEX  CON  INT  LUK      │  아이템 설명     │
│  캐릭터2  │  14   24★  13   10   22◆     │  또는           │
│  캐릭터3  │──────────────────────────────│  캐릭터 요약     │
│          │  소유 아이템 격자 / 시트      │                 │
└──────────┴──────────────────────────────┴─────────────────┘
```

**항상 열 수 있다** — `BattleHud.Update`가 매 프레임 TAB을 검사하며, 캔버스 정렬 순서가 120이라
보상·사건 같은 모달(80)보다 위에 뜬다. 어느 페이즈에서든 아이템 보유자와 장착을 지정할 수 있다.

**주스탯 스트립** — 레퍼런스의 `근접 +N / 명중 보너스 / 피해` 줄 자리에 **5주스탯**을 놓는다.
주스탯은 ★, 부스탯은 ◆로 표시하고 앰버로 강조한다. 소유 아이템 격자 바로 위에 항상 보인다.

**캐릭터 시트 탭** — 네 구획을 순서대로 쌓는다.

| 순서 | 내용 |
| --- | --- |
| 1. 기초 스탯 | STR / DEX / CON / INT / LUK |
| 2. 상세 스탯 | 체력, 방어력, 내구, 위력 100 기준 피해, 치명타(확률·배율), 행동 속도, 마나 효율 |
| 3. 육성 | 육성 Lv, 중량 `현재 / 한도`, 보유 코드 수 |
| 4. 상태 | 지금 걸려 있는 상태를 전투 카드와 **같은 아이콘**으로. 없으면 구획 자체가 빠진다 |

**코드는 별도 탭이다.** 고유 패시브·일반행동·궁극기와 해금·전수·장비 코드를 한 목록에 놓고
등급(은·금·보라)으로 색을 준다. **코드 용량 한도는 폐지됐으므로 `보유 / 최대` 표기는 없다.**

**추천 조합 탭** — `30_synergies.yaml`을 `SynergyCatalog`이 읽어 유닛 칸마다 채운다.
기획 원본은 [Detail_15](Detail_15_Party_Synergy.md)다.

| 순서 | 내용 |
| --- | --- |
| 1. 역할 | 역할군 ID를 한국어 이름으로 풀어 나열 |
| 2. 기여 | 전투·육성 기여를 ●○ 눈금 5칸으로. 권장 열(전열/후열) 병기 |
| 3. 강점 | `provides[].text` 를 줄바꿈 되는 문단으로 |
| 4. 주의 | `caution`. 붉은색 |
| 5. 편성 | **메인 가능**이면 고점·대체 두 벌을 아키타입 이름과 함께. **서포트 전용**이면 이 캐릭터를 부르는 메인 목록 |

**아직 손에 넣지 못한 이름은 흐리게 찍는다**(`SynergyCatalog.IsAvailable`).
Support 유형은 언제나 편성 가능하므로 항상 밝게 나오고, Starter·Locked는 해금·육성 기록을 본다.
"지금 짤 수 있는 조합"과 "다 모으면 되는 조합"이 같은 화면에서 갈린다.

### 1.6 캐릭터 선택 화면

철권 캐릭터 셀렉트를 레퍼런스로 삼는다. 후보를 **초상화 타일 격자**로 늘어놓고,
커서를 올린 캐릭터의 **큰 초상화**를 좌측에 띄운다.

**그림은 초상화(Portrait)만 쓰고 타일·미리보기 모두 정사각형으로 고정한다.**
초상화 원본이 정사각형이므로 칸이 정사각형이면 여백 없이 딱 맞는다.
스탠딩은 세로로 길어 같은 칸에 섞으면 비율이 무너지므로 이 화면에서는 쓰지 않는다.

칸 크기는 `SquareGridSizer`가 격자 영역의 실제 픽셀 크기에서 매번 다시 계산한다.
캔버스 스케일은 첫 프레임에 확정되지 않고 창 크기에 따라 또 바뀌므로 한 번만 재면 어긋난다.

```
┌──────────────┬──────────────────────────────────────┐
│              │  1단계: 메인 캐릭터                   │
│   큰 초상화   │  ┌────┬────┬────┬────┬────┬────┐     │
│              │  │ 초상│ 초상│ 초상│ 초상│ 초상│ 초상│     │
│   캐릭터명    │  │ 이름│ 이름│ 이름│ 이름│ 이름│ 이름│     │
│   한 줄 소개  │  └────┴────┴────┴────┴────┴────┘     │
│   원소·주/부  │  메인  수르트 / 서포터 —              │
│   운용·분류   │  추천  바루나 · 잔 · 마리 · 프레이아   │
│              │   [← 뒤로]  [★ 추천 편성]  [다음 →]   │
└──────────────┴──────────────────────────────────────┘
```

**미리보기 설명.** 한 줄 소개(`10_units.yaml`의 `tagline`) → 원소·주/부 스탯 → 메인 단계에서는
운용 축(`30_synergies.yaml`의 `axis`) → 편성 자격 순으로 싣는다.

**서포터 추천.** 2단계에 들어서면 고른 메인의 추천 조합(`30_synergies.yaml` `recommendations`)으로
추천 서포터 넷을 정한다. **고점 조합(`best`)에서 지금 격자에 오른 사람을 먼저** 담고, 빈자리는
최초 로스터만 쓰는 대체 조합(`basic`)으로 채운다 — 해금이 덜 된 계정에서도 네 자리가 비지 않는다.
추천 타일에는 `★ 추천 N` 띠가 붙고, 요약 줄에 이름·조합명·이유의 첫 문장이 뜬다.
`★ 추천 편성`은 서포터 칸을 추천 넷으로 통째로 바꾼다. 메인은 건드리지 않는다.
무한 모드는 메인이 없으므로 추천도 없다.

**모드별 흐름**

| 모드 | 단계 |
| --- | --- |
| 육성 | 1단계 **메인 1명** → `다음` → 2단계 **서포터 카드 4명** → `여정 시작` |
| 무한 | 메인 단계 없이 **서포터 카드 5장**을 바로 고르고 `여정 시작` |

- 1단계 후보는 `canStartAsMain` 또는 해금된 캐릭터, 2단계 후보는 `canStartAsSupport`만 보여준다
- 메인 단계에서 다른 타일을 누르면 기존 선택을 갈아 끼운다(항상 1명)
- 이미 고른 타일을 다시 누르면 해제된다
- `뒤로`는 2단계에서만 보이며 누르면 편성을 비우고 1단계로 돌아간다

### 1.7 사건(VN) 진행 조작

| 버튼 | 동작 |
| --- | --- |
| `계속 ▸` | 대사 한 줄 진행 |
| `자동` | 켜면 일정 시간마다 스스로 다음 대사로 넘어간다. 다시 누르면 해제 |
| `건너뛰기 ▶▶` | 남은 대사를 전부 건너뛰고 선택지로(없으면 사건 종료로) 간다 |

자동 대기 시간 = `1.2초 + 글자 수 × 0.045초` (상한 6초).
긴 대사일수록 오래 머물러 읽을 시간이 남는다.

**선택지·결과 화면에서는 자동이 꺼지고 세 버튼이 모두 숨는다.** 선택은 플레이어가 해야 한다.

> 화면은 MonoBehaviour가 아니므로 타이머는 `UIManager.Update()`가 매 프레임 넘겨 준다.

### 1.8 전장 초상화 크기 정규화

초상화 원본 해상도가 제각각이다 — 아군 1254px, 적 512px, 일부 1024px.
`Cell`의 스프라이트 렌더러 배율을 고정해 두면 **아군은 칸을 넘치고 적은 칸의 절반만 채운다.**

`Cell.SetPortrait`가 긴 변을 `PortraitFitSize`(9.6, 칸 테두리 10.16보다 약간 안쪽)에 맞춰
균일 배율로 줄인다. 해상도와 무관하게 항상 칸에 꼭 맞고 비율도 유지된다.
드래그 미리보기도 같은 배율을 따른다.

### 1.9 전장 카메라 프레이밍

배치 상수를 바꿀 때마다 씬의 카메라를 손으로 옮기면 금방 어긋난다.
`GridManager.FrameCamera()`가 **실제로 만들어진 셀 좌표에서 경계를 구해** 그 중심에 카메라를 두고
`orthographicSize`를 잡는다. 전열/후열 간격이나 대기석 위치를 바꿔도 프레이밍이 따라온다.

HUD가 판을 덮지 않도록 위아래로 여유를 더 준다.

| 여유 | 값 | 이유 |
| --- | --- | --- |
| `CameraTopHudFraction` | 0.07 | 상단 상태바가 최상단 행을 가린다 |
| `CameraBottomHudFraction` | 0.16 | 준비 페이즈 바가 대기석을 가려 유닛을 내려놓을 수 없다 |

아래 여유는 **준비 단계에만** 준다. 전투 중에는 그 바가 사라진다.

**전투 중에는 대기석을 숨긴다.** 유닛을 옮길 수 없어 자리만 차지하기 때문이다.
`SetBenchVisible(false)`가 대기석을 끄고 카메라 계산에서도 빼므로 전장이 그만큼 확대된다.
`OnRoundStart`에서 끄고 `OnRoundEnd`에서 되돌린다.

> 🔸 **씬에 저장된 범위가 구조를 깨뜨릴 수 있다.**
> `CalculateFieldCellPosition`은 |x|=1을 전열, 그 외를 후열로 보므로 x가 ±2를 넘으면
> 여러 x가 같은 좌표로 계산되어 셀이 겹쳐 쌓인다. 실제로 씬에 구 레이아웃 값
> (`xMin -3 / xMax 3 / yMax 3 / benchSize 9`)이 남아 x=−3과 −2가 포개져 있었다.
> `EnforceLayoutBounds()`가 진영당 2열 × 4행, 대기석 5칸으로 바로잡고 경고를 남긴다.

## 1.10 공격 연출 — 무기 분류별 유형

**공격 하나가 어떤 모양으로 보일지는 `Effects.AttackVisuals`가 혼자 정한다.**
피해 태그의 5만 번대(무기 분류)가 최우선이고, 태그가 없으면 **손에 든 무기**를 본다.
장비가 비어 있으면 `startingProficiencies`로 물러난다(적 유닛은 장비 없이 서기 때문이다).

| 유형 | 결정 조건 | 화면 |
| --- | --- | --- |
| **베기** `Slash` | `Slash` 태그, 또는 장검·대검·단검 | 대상 카드 위를 비스듬히 긋는 선 + 파편 |
| **찌르기** `Thrust` | `Pierce` 태그, 또는 장창·단창 | 공격 방향을 따라 들어왔다 빠지는 창 + 앞으로 뻗는 파편 |
| **타격** `Impact` | 물리인데 무기 분류가 없음(둔기·맨손·투척) | 방향 없는 충격 고리 두 겹 + 사방 파편 |
| **화살** `Arrow` | `Arrow` 태그, 또는 활·석궁 | 깃 달린 투사체가 포물선으로 날아감 |
| **마법·특수** `Bolt` | `Physical`이 없는 모든 공격 | 원소색 마름모가 직선으로 날아감 |

**근접이냐 투사체냐는 무기가 정한다.** 일반행동의 기본 태그가 비접촉이라 접촉 태그만 보면
검사도 창병도 빈손으로 빛을 쏘게 된다. 베기·찌르기는 언제나 대상 위에서 터지고,
화살·마법은 언제나 날아간다. 타격만 둘 다 된다 — 둔기를 들었거나 접촉 태그가 있으면 내려치고,
맨손 비접촉이면 **덩어리가 돌면서 날아가(`Thrown`)** 고리로 터진다.

> 예전에는 `SfxManager`가 "검 숙련이면 베기, 로마·메히코면 베기"라는 두 줄짜리 예외만 갖고
> 나머지를 전부 같은 빛덩이로 쐈다. 창병도 둔기병도 구분되지 않았다.

**색은 시전자의 원소색이다.** 카드의 궁극기 링과 같은 표(`ElementalProjectiles`)를 쓰므로
날아가는 색만 봐도 누가 쏜 것인지 읽힌다. 궁극기는 파스텔, **물리는 원소색을 30%만 강철로 물려**
마법과 갈라 둔다. 원소가 없는 유닛(None)의 물리는 그냥 강철색이다.

**투사체는 아트 에셋이 아니라 코드로 그린다.** `ProjectileShapes`가 마름모·잔광·고리·파편
스프라이트를 만들어 캐시하고, `CardProjectile`이 그것을 조립해 쏜다. 파티클을 뿌리는 대신
**또렷한 실루엣 하나**를 짧고 세게 쓰는 쪽이다.

**궤적은 두 가지만 쓴다.**

| 궤적 | 대상 | 계산 |
| --- | --- | --- |
| **직선형** `Linear` | 마법·특수 투사체, 접촉(근접) 물리 | `Lerp(start, end, t)` |
| **곡선형** `ParabolicArc` | 화살·투척 등 **원거리 물리** | `Lerp` + `4h·t(1−t)`, 최고 높이 5 |

선택은 `ProjectileFlight.PathFor(피해 태그)`가 한다 — `Physical`이면서 `ContactAttack`이 아니면 곡선형,
그 외에는 직선형이다. 접촉 물리를 뺀 이유는 붙어서 때리는 연출에 포물선을 씌우면
이펙트가 솟았다 내려와 타격감이 어긋나기 때문이다.

> 🔸 **나머지 경로 타입(Spiral·Wave·Bezier·MultiPoint·DelayedDrop)은 구현만 남기고 쓰지 않는다.**
> 이 게임은 XY 평면을 정사영으로 비추는데, 그 경로들은 오프셋을 **경로에 수직인 z축**으로 준다.
> Wave는 전량이 z라 화면에서 아무 변화가 없었고, Spiral은 절반만 y라 나선이 아니라 위아래 진동으로 보였다.
> 곡선형은 y를 직접 올리므로 2D에서 그대로 보인다.

**파일 위치** — `Scripts/Effects/`
(`AttackVisuals` 판정 · `MeleeVfx`의 찌르기/타격 · `CombatVfx`의 베기/에어본 · `CombatFeedback` 타격 반응)
`Scripts/Effects/Projectiles/`
(`CardProjectile` · `ProjectileShapes` · `ProjectilePathType` · `ProjectilePathData` · `ProjectileFlight`)
`HS_ProjectileCustomMover`는 이 프로젝트가 작성한 코드인데 벤더 폴더(`Hovl Studio/`)에 있었다.
에셋을 다시 임포트하면 덮어써질 자리라 Scripts로 옮겼다.

## 1.11 타격 피드백

전투가 자동으로 굴러가므로 **무엇이 얼마나 아팠는지**를 체력 바의 변화만으로 읽게 두면 놓친다.
피해가 정산된 자리(`Unit.DefaultTakeDamageEvent`)에서 `Effects.CombatFeedback`이 세 가지를 함께 친다.
하나만으로는 약하고, 셋이 같은 프레임에 겹쳐야 '맞았다'가 된다.

| 반응 | 내용 |
| --- | --- |
| **숫자** | 맞은 자리에서 튀어 올랐다 떠오르며 사라진다(`DamagePopup`). 체력에 들어간 피해는 흰색, 방어막이 대신 받으면 방어막색, 회피는 '회피', 횟수제 무적이 막으면 방어막색 '무효', 치명타는 **금색 + 굵게 + 1.35배** |
| **카드** | 하얗게 번쩍이며 뒤로 밀리고, **물리 타격이면 떤다**(`UnitCardView.PlayHitReaction`). 마법은 떨지 않고 번쩍이기만 한다 |
| **화면** | 큰 한 방에만 아주 짧게 흔들린다(`CameraShake`) |
| **시간** | 치명타 · 궁극기 · 한 방이 큰 공격에서만 **30~50ms** 멈춘다(`HitStop`) |

**전투 자원은 카드 이름표에 붙는다**(`Combat.CombatResourceLabels`). 이름이 등록된 자원은 전부 띄우고
0이면 숨긴다 — 천공 전선의 `무적 N` · `발동까지 N` · `포만 N`, 해안 전선의 `구간 N/6`. 켜짐만 알리면 되는 자원은 숫자 없이 이름만 띄운다 — 해안의 `갑주` · `준비`. 이름이 없는 자원(가우디의 스택 등)은
예전처럼 첫 하나만 `◆현재/최대`로 띄운다. 소환체는 무적과 카운트다운을 **함께** 보여야 우선순위를 읽을 수 있어서다.

> 🔸 **숫자는 대상을 따라가고, 대상을 잃으면 화면 좌표에 못 박는다.**
> 생성 시점의 월드 좌표를 붙들고 있으면 허공에 숫자가 남는다 — 유닛이 쓰러지면 칸이 비고,
> 빈 칸이 지워지며 남은 카드가 가운데로 다시 모이고 카메라까지 다시 잡히기 때문이다.
> 실제로 전장 빈 자리에 433이 떠 있었다. 마지막 일격의 숫자를 지우지 않으려고
> **즉시 종료가 아니라 그때의 화면 좌표에 고정**하는 쪽을 택했다.

**멈춤(hit-stop)은 자격을 좁게 준다.** 잔매마다 서면 전투가 끊긴 것으로만 보인다.
치명타이거나, 궁극기이거나, 한 번에 최대 체력의 **55%** 이상을 깎았을 때만 선다.
멈춤 사이 최소 간격은 **0.12초**이고 길이는 **실시간**으로 재므로 8배속에서도 같은 길이다.
배속이 `Time.timeScale`이라(§1.2) 멈춤은 그 값을 기억했다가 되돌리며,
되돌릴 때 <b>우리가 넣어 둔 값이 그대로 남아 있을 때만</b> 손댄다.

**세기는 절대 피해량이 아니라 "최대 체력의 몇 할을 한 번에 잃었는가"로 잰다.** 같은 50이라도
레벨에 따라 뜻이 달라지기 때문이다. **22%**를 한 번에 깎으면 최대 세기가 되고, 숫자 크기도
같은 값을 따라 커진다. 지속피해는 때린 사람이 없으므로 떨림을 **35%**로 줄이고 화면은 흔들지 않는다.

**때리는 쪽도 움직인다.** 근접은 타격 순간 적 방향으로 찍고(1.15), 물리 원거리는 쏘는 반동으로
조금 물러난다(0.8). 맞는 카드만 흔들리면 누가 쳤는지가 화면에서 사라진다.

> 🔸 **카메라 흔들림은 프레이밍과 싸우지 않는다.** 카메라 위치의 주인은 `GridManager.FrameCamera()`다.
> `CameraShake`는 매 프레임 **직전에 넣은 흔들림을 먼저 빼고** 기준 위치를 다시 읽으므로,
> 전투 중 빈 칸이 지워져 프레이밍이 다시 잡혀도 카메라가 옛 자리로 끌려가지 않는다.

**연출 점검** — Editor에서 `Tools/Combat VFX/Export Preview` (Ctrl+Alt+V)가 베기·찌르기·타격·에어본을
한 장의 PNG(`Temp/CombatVfxPreview.png`)로 굽는다. 플레이 모드에 들어가지 않고 모양만 확인할 때 쓴다.

## 1.12 전장 배경 — 테마 환경광

완전한 검정 배경은 카드 대비에 가장 유리하지만 **어디서 싸우는지**가 사라진다.
로마 군단도 공허 얼음도 같은 검은 방에서 싸우는 것처럼 보인다.

`Effects.BattlefieldBackdrop`이 카메라에 붙어 세 겹을 깐다. 모두 명도가 낮아 카드를 덮지 않는다.

| 겹 | 내용 |
| --- | --- |
| 하늘 | 위는 거의 검고 아래로 갈수록 테마 색이 밴다(최대 알파 0.30) |
| 바닥 | 아주 옅은 사선 빗금. 평면이 바닥으로 읽히게 하는 결이다(0.13) |
| 광원 | 전장 가운데의 넓고 부드러운 빛 웅덩이(0.18) |

색은 테마마다 `80_stages.yaml`의 `ambientColor`(#RRGGBB)가 정한다. 비워 두면 무채색 기본값이다.
아래쪽이 밝아지는 만큼 적 실루엣도 배경에서 떨어져 나온다.

> 🔸 **배경은 가장 아래 정렬 레이어에 둔다.** `sortingOrder`만 낮추면 카드가 다른 정렬 레이어를
> 쓸 때 배경이 카드를 덮는다. 카메라의 자식이라 프레이밍이 다시 잡혀도 따라온다.

**텍스트 대비 기준선은 4.5:1이다.** 가라앉은 면(`SurfaceSunken`) 위에서 잰다.

| 색 | 쓰임 | 대비 |
| --- | --- | ---: |
| `TextPrimary` | 이름·값 | 17:1 |

도형으로 그린 빈 상태 판과 **행동 유도 버튼**을 세운다. 버튼을 누를 수 없는 상황이면
버튼을 끄는 데서 그치지 않고 **왜 못 누르는지**를 함께 적는다 — 꺼진 버튼만 남기면 고장으로 읽힌다.

### 1.4 셀 UI 규칙

**카드 HUD는 8배속에서 읽혀야 한다.** 자동 전투라 플레이어가 할 수 있는 일은 보는 것뿐인데,
그 화면이 가장 빠를 때 읽히지 않으면 아무것도 읽히지 않는 것과 같다.

| 자리 | 규칙 |
| --- | --- |
| **궁극기 게이지** | 우상단 원형. 아래에서 위로 차오르고, 안에 **⌃⌃ 표식**이 흐리게 깔린다 — 원소색 원반 하나만으로는 "원소 표시"인지 "충전량"인지 갈리지 않기 때문이다. 다 차면 표식이 또렷해지며 맥동하고 테두리가 금색으로 넘어간다 |
| **상태 아이콘** | 어두운 원형 받침 위에 그림. 같은 Key는 **한 칸에 모으고 중첩 수를 오른쪽 아래에 적는다**(1이면 적지 않는다) |
| **상태 색** | 이로움 초록 · 해로움 적색 · **행동 불가 보라**(`UITheme.Control`) |

> 중첩은 같은 상태를 여러 개 들고 있는 것으로 구현돼 있어(`StatusStackPolicy.Stack`),
> 목록을 그대로 늘어놓으면 화상 5중첩 하나가 다섯 칸을 전부 먹었다.

> 행동 불가를 적색에 섞어 두면 "그냥 나쁜 것"으로만 읽힌다. 지금 못 움직이는 유닛이
> 다른 디버프 사이에서 색 하나로 먼저 튀어나와야 한다.

중첩 수 글자는 `UIShapes.Digit`이 3×5 격자를 블록으로 찍어 만든다. TextMeshPro를 쓰지 않는
이유는 이 캔버스가 월드 스페이스라서다 — `TextMeshProUGUI`는 여기서 아예 그려지지 않고(§1.2의
카드 이름표가 겪은 문제), 카드마다 월드 텍스트를 몇 개씩 세우는 것은 두 자리 숫자 하나에 과하다.

| 규칙 | 내용 |
| --- | --- |
| 책임 분리 | `Unit.cs`는 게임 로직, `Cell.cs`는 UI 표시 |
| 필드 전용 | 대기석 유닛은 UI를 표시하지 않는다 |
| HP 바 | 체력 100% = scale 9, 위치 이동으로 감소 표현 |
| **z값 통일** | 모든 바의 z = 0 |
| 깊이 제어 | z축이 아닌 **`SpriteRenderer.sortingOrder`** 사용 |

```csharp
// HP 바 스케일 계산
float targetScale = hpRatio * 9.0f;
float xOffset = (9.0f - targetScale) * -0.5f;

// 렌더 순서
currHpRenderer.sortingOrder = maxHpRenderer.sortingOrder + 1;
```

> **교훈** — 2D에서는 z축 위치보다 `sortingOrder`가 안정적이다.
> 과거 HP 바에 임의 z값(-0.1f)을 쓴 결과, 드래그 앤 드롭의 z 좌표계와 충돌해 위치가 왜곡됐다.

## 1.13 엘리트·보스 단독 연출

**판정이 둘이다.** 상단 체력 띠와 카드 확대는 조건이 다르다. 띠는 화면 위쪽의 빈 자리를 쓰지만
커진 카드는 옆 칸을 침범하므로, 잡졸이 함께 선 판에서 카드를 키우면 서로 가린다.

| | 상단 체력 띠 | 카드 확대 |
| --- | --- | --- |
| 판정 | `FeatureEnemies.BannerTargets()` | `FeatureEnemies.SoloStageTargets()` |
| 조건 | **엘리트가 하나라도 있으면** | 살아 있는 적이 1~2기이고 **전원이** 엘리트·보스 |
| 인원 | 최대 2 (`MaxCount`). 셋 이상이면 보스 먼저, 그다음 최대 체력 순 | 1~2 |
| 효과 | 상단 중앙에 이름·체력·상태 | `Cell.FeatureCardScale` = **1.5배** |
| 적용 시점 | 매 프레임 (`BattleHud.Update`) | 편성 배치 직후 (`RoundManager.ApplyFeaturePresentation`) |

호위를 달고 나오는 중간 보스는 **띠는 뜨지만 카드는 그대로**다. 라그나르가 광전사 둘과
볼바 둘을 데리고 서는 4슬롯이 그 경우다.

**카드 확대는 칸 안에서 일어난다.** `Cell.SetFeatureScale`이 카드와 초상화에 같은 배율을 먹인다.
초상화는 카드와 별개의 렌더러라 배율을 직접 다시 먹여야 하므로, 스케일을 바꾸면
`SetPortrait`를 다시 태운다. 옆 칸이 비어 있을 때만 켜지므로 커진 카드가 다른 유닛을 가리지 않는다.

### 상단 중앙 체력 띠 (`FeatureEnemyBanner`)

자원 표시줄 아래에 붙는다. 한 명이면 폭 560을 다 쓰고, 둘이면 가운데 틈을 두고 반씩 나눈다.
칸 하나에 이름과 체력 바, 현재/최대 수치, 상태 아이콘 여섯 개까지 들어간다.

카드 위의 작은 바는 **잡졸 다섯을 한눈에 훑기 위한 것**이라, 한 마리를 오래 때리는 판에서는
정보가 너무 멀리 있다. 2인조에서 좌우로 나누면 둘 중 누구를 먼저 깎고 있는지가
화면 한가운데에서 읽힌다. 방어막은 체력 바 위에 겹쳐 그려 껍질이 남았는지를 함께 보여 준다.

### 2.1 단일 진입점 원칙

`RunManager.AdvanceToNextStage()` — 보상/사건/육성 어느 흐름에서 오든 여기를 통과한다.

```
if (육성 모드) {
    if (Stage >= MaxTrainingStage || !TryLoadNextRound())  → CompleteTrainingRun()
    else                                                    → 세이브 + 다음 스테이지

    else                       → 세이브 + 다음 스테이지
}
```

### 4.4 저장/삭제 시점

| 시점 | 동작 |
| --- | --- |
| 스테이지 전진 | `SaveCurrentRun()` |
| 전투 시작 직전 | `SaveCurrentRun()` |
| 사건 발생 기록 | `MarkEventTriggered()` → 즉시 저장 |
| 앱 일시정지 / 종료 | `OnApplicationPause` / `OnApplicationQuit` — `CanSaveNow`일 때만 |
| 인게임 메뉴 `저장` · `저장 후 나가기` | `SaveCurrentRun()` — `CanSaveNow`일 때만 |
| 런 시작 | `SaveSystem.DeleteSave()` — 기존 진행 폐기 |
| 게임 오버 / 런 완료 | `SaveSystem.DeleteSave()` |

**`RunManager.CanSaveNow`** — 준비 · 육성 · 사건 페이즈에서만 참이다. 전투 중에 저장하면 쓰러진 아군이
`BuildHeroSaveData`에서 빠지고, 보상 선택 중에 저장하면 경험치를 받은 채 같은 전투로 되돌아가며,
캐릭터 선택 중에는 파티가 비어 있다. 그때는 전투 직전 자동 저장을 그대로 두고 덮어쓰지 않는다.

인게임 메뉴의 `불러오기`는 `GameStartIntent.Continue`로 Game 씬을 다시 연다. `메인 메뉴로 나가기`는
저장하지 않는다 — 마지막 저장 이후의 진행을 버리는 출구이고, 메인 메뉴의 이어하기로 그 시점부터 잇는다.

### 4.5 복원 순서

```
LoadSavedRun()
  1. 모드/생명력/킬 수 복원
  2. 인벤토리 복원 (토큰, 골드, 티켓, 아이템)
  3. 우정도 / 사건 이력 복원
  4. RoundManager.InitializeStage(stage)
  5. 기존 아군 전부 비활성화 → 저장된 아군 스폰 → RestoreRunState()
  6. RoundManager.LoadRound(stage)
  7. UI 갱신 → EnterNextStageAfterLoad() → 준비 행동 상태 복원
```

**구버전 세이브는 로드 시 폐기된다** (`RunSaveData.version`).

## 4.6 디버그 모드 (에디터 · 개발 빌드 전용)

전투가 완전 자동이라 **확인하고 싶은 장면에 도달하는 방법이 정상 플레이뿐이다.**
테마 하나를 보려면 라운드를 그만큼 지나야 하고(테마는 `(Round-1) % 활성테마수`로 정해진다),

`Core/DebugMode.cs`(상태) + `Managers/UI/DevTools/DebugOverlay.cs`(패널).
둘 다 `#if UNITY_EDITOR || DEVELOPMENT_BUILD`으로 감싸 **출시 빌드에는 들어가지 않는다.**
호출부(`Unit.TakeDamage`·`RoundManager.EnsureThemeForCurrentRound`·`GameManager.HandleDebugInput`)도
같은 조건으로 감쌌다.

- 무적은 `Unit.TakeDamage` **입구**에서 자른다. 지속피해·고정피해까지 한 곳에서 막기 위해서다.
- 테마 고정은 **다음 스테이지 로드부터** 적용된다.

`SpriteResource`가 위 네 분류 폴더를 먼저 뒤지고 이전 평면 루트를 마지막으로 본다. 따라서 YAML과
코드에는 분류 경로를 넣지 않고 기존 스프라이트 키를 그대로 유지한다. 아군·적이 같은 원화를 공유하는
경우에는 파일을 `Allies`에 한 번만 두고 양쪽에서 같은 키로 불러온다.

> **초상화·스탠딩은 `Resources.Load`를 직접 부르지 않는다. 반드시 `SpriteResource`를 거친다.**
> 데이터가 들고 있는 것은 키(`SEI_PORTRAIT`)이고 실제 파일은 분류 폴더 안에 있어서, 키를 그대로
> `Resources.Load`에 넘기면 **조용히 null이 돌아온다.** 분류 폴더로 옮기던 날 소환수 카드·행동
> 대기열·도감·육성 화면이 한꺼번에 빈 칸이 된 것이 이 때문이다.
> `SpriteResource`는 키와 해석이 끝난 전체 경로를 모두 받으므로 진입점을 하나로 둘 수 있다.
>
> `Unit.PortraitPath`는 **해석에 성공하면 전체 경로, 실패하면 키 그대로**를 담는다. 어느 쪽이든
> 그대로 `SpriteResource.LoadPortrait`에 넘기면 된다.
>
> 아이템 아이콘(`Sprite/Items/`)만은 분류가 없는 평면 폴더라 직접 로드해도 된다.

디버그 검증(F1 → 전체 검증)의 **스프라이트 연결** 단계가 유닛·적·아이템·소환수의 키를 전부 한 번씩
읽어 본다. 자산을 옮기거나 이름을 바꾸면 이 단계가 먼저 깨진다.
